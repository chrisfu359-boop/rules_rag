## P7 · 检索链路（对应任务 3.1–3.6）

```
【任务】实现完整检索链路：双向量召回 + BM25 + RRF 融合 + reranker 精排，并修掉从 EduRAG 继承的两个缺陷。

【模块】
1. retrieval/indexer.py
   - 用 BGE-M3 对 t_clause.content 编码，同时取 dense 与 sparse
   - 批量写 Milvus（batch=64），字段映射见 docs/04 §2.2
   - 输出进度与总耗时

2. retrieval/vector_store.py（基于 EduRAG 改造，必须修 2 个缺陷）
   - 缺陷 A【致命】：原 `_get_unique_parent_docs` 用 set 去重正文后 `Document(page_content=content)`，把 parent_id/source/timestamp 全丢了。
     改成：去重必须保留完整 metadata（用 dict 按 parent_id 去重，不是 set 存字符串）。
     修完写一个单测证明：重排后仍能取到 clause_id 与 source_url。
   - 缺陷 B：原检索只支持单值等值过滤（source=='x'），不支持范围。
     改成：构造 Milvus 表达式 `status == "active" and effective_from <= {now} and effective_to > {now}`，
     并支持 category/platform/scene/state_in 的"空则通配"语义。
   - 关键：**过滤条件必须在 search 的 expr 里，不许召回后再 filter**。代码注释里写明原因。

3. retrieval/bm25_search.py（修缺陷 C）
   - 原代码对 BM25 分数做 softmax 后判 >= 0.85 —— BM25 分数无上界，softmax 结果依赖候选集大小，阈值没有物理意义。
   - 改成双条件：top1 绝对分 >= 阈值A，且 (top1 - top2) >= 阈值B。两个阈值都放进配置，并在注释里说明取值依据。
   - 用 MySQL ngram 全文索引实现，不要引入 Elasticsearch。

4. retrieval/fusion.py
   - RRF（k=60）融合 dense / sparse / bm25 三路
   - reranker 用 bge-reranker-base，只对 top20 精排，取 top5
   - reranker 懒加载：首次调用才加载，加载后打印内存占用

5. 检索评估 eval/eval_retrieval.py
   - 输入 data/eval/retrieval_50.csv（query + gold_clause_id，初始可只有 20 条）
   - 输出 Recall@5、MRR，并**分层报数**（按时效/类目/场景三类过滤场景分）
   - 结果写 reports/retrieval_eval.md

【验收（全部要贴真实输出）】
- 500 条条款入库耗时
- 单次 query 的端到端延迟（embed + 召回 + 融合 + 重排），P50/P95
- "失效条款是否会进入候选集"的专项测试：造一条 expired 条款，证明过滤后它不出现在结果里
- 召回与不召回的对比：同一 query，带过滤 vs 不带过滤的 top5 差异，用来说明"先过滤再召回"的必要性

【内存纪律】embedding 与 reranker 不许在同一进程常驻。若必须同进程，先报告内存峰值再决定。
```
