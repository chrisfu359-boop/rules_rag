# 14 · 智能客服：从"查规则"到"接客"

> 只做规则查询的系统是个题库，不是产品。商家真正每天在干的事是回消息，
> 而回消息里 70% 是可以被复用的话术。这一层要解决的就是：让机器人吃掉那 70%，
> 剩下的 30% 带着上下文落到人手上。

## 一、为什么是四级漏斗，而不是"直接问大模型"

一道题如果每次都送到模型，成本、延迟、稳定性三样全崩：

| 方案 | 单次成本 | P50 延迟 | 答案稳定性 |
|---|---|---|---|
| 全部走大模型 | 有 token 费 | 1~3s | 每次措辞都不同 |
| 全部走人工 | 人力 | 分钟级 | 稳定但不可扩展 |
| **本方案：四级漏斗** | 前两级几乎为零 | 命中前三级的都在 100ms 内 | 命中的是固定话术 |

所以顺序是**按成本从低到高**排的，每一级都只处理上一级漏下来的：

```
用户提问
  │
  ├─① Redis 精确缓存 ──────────── 命中即返回           ~20ms
  │      key = 归一化问句 + 知识库版本号 + 模型名
  │
  ├─② FAQ 库 BM25 ≥ 0.88 ─────── 命中即返回标准答案    ~30ms
  │      74 条平台通用问答对 + 每店专属话术（和 406 条规则库是两套东西，会随沉淀增长）
  │
  ├─③ 大模型（带 FAQ 候选做上下文） 有把握就答         1~3s
  │      输出仍要过引用校验，编造条款号直接降级
  │
  └─④ 人工兜底（工单）─────────── 生成工单 + 排队 + 坐席接管
```

## 二、一个窗口，三个板块

最早的错误是把"咨询窗口"当成一个东西。买家打开它问"什么时候发货"；商家打开它，
问的还是"什么时候发货"——对着自己的店。截图里就是这样：商家登录后看到
「霞光家居旗舰店 · 在线客服」，快捷问题是"什么时候发货 / 几天能到 / 能便宜点吗"。
他会以为平台让他自己哄自己。

根因不在界面，在数据：`t_faq` 只有一个知识库，`t_cs_session` 不区分会话类型。
三个角色共用一条漏斗，就只能共用一套答案。

现在按"这条知识回答谁"切成三个知识域（`t_faq.audience`），会话也带上了板块（`t_cs_session.scope`）：

| 板块 | 谁进 | 问什么 | 知识域 | `scope` |
|---|---|---|---|---|
| 店铺客服 | 买家 | 这家店多久发货、能不能退 | `buyer`（平台通用 74 + 每店专属） | `shop` |
| 平台规则助手 | 商家 | 这样算不算违规、扣几分、怎么申诉 | `merchant`（21 条） | `rule` |
| 治理规范助手 | 平台运营 | 该引哪一条、法律怎么规定、能不能这么判 | `ops`（20 条） | `gov` |

三个板块的差别是实质的。同一句「扣几分」：

- **买家问** → 店铺客服答不上来，转人工（这本来就不是店铺能回答的问题）
- **商家问** → 「2.4 发货超时，每单扣 0.5 分」
- **运营问** → 「依据 4.2.2，满 12 分限制参加营销活动 30 天」

### 三个技术决定

1. **索引按域分开建，不是建一个大索引再过滤。** 过滤是"先取 top5 再筛"：
   别的域的条目一旦排进前 5，本域正确的答案就被挤出去了，用户看到的是
   "知识库没有这条"。这是分域检索最容易写错的地方。
2. **缓存 key 带知识域**（`rr:cs:v{ver}:{aud}:q:{md5}`）。不带的话，商家问过的
   「七天无理由运费谁承担」会被运营直接命中，答的却是商家口径。这类 bug 只在
   特定提问顺序下复现，最难查。
3. **会话 `scope` 决定它进谁的队列。** 商家问规则的会话 `shop_id` 为 NULL，
   不会出现在客服工作台的待处理队列里——坐席点开一条"售假扣几分"，
   能做的最多是把答案再念一遍。

### 快捷问题由服务端生成

页面上那排 chip 以前是写死的。写死的问题不是"不好看"，是会和知识库脱节：
点下去知识库没有，直接掉进人工兜底，用户以为系统坏了。

现在 `GET /api/cs/board` 按当前账号的知识域，从 `t_faq` 取高频问法生成 chips，
并做两件事：

- 同分类最多两条（否则六个 chip 全是发货问题，看起来只有一个板块）
- **排除会被强制转人工规则截走的问题**。知识库里确实有一条「转人工」，
  但只要文本含"转人工"，`force_handoff` 在检索之前就拦了——这个 chip 点下去
  永远是"已转接人工"。宁可不出。

最后再补一条**不走普通检索**的入口，让第四层漏斗在页面上看得见，而不是只写在文档里。
三条的性质并不一样，这一点以前没分清：

| 板块 | 最后一格 | 点下去发生什么 |
|---|---|---|
| 店铺客服 | 转人工 | 买家主动要求人工 → 建工单、转店家客服 |
| 平台规则助手 | 我的店被扣分了 | 助手没有账号数据 → 转平台规则运营 |
| 治理规范助手 | 挑一单查条款 | **弹案件选择器**，选中后摊事实与条款，不给结论 |

治理板块原来写的是「这个案子怎么判」。这句话有三个问题：`这个`没有指代对象
（窗口里根本没选中任何案子）；点下去必然撞 `case_judge` 规则被拦成转人工；
而且和板块自己写的"不对在办案件下结论"直接打架。详见下面「带单核查」。

### 三个板块的"人工"不是同一个人

| 板块 | 拦住什么 | 转给谁 |
|---|---|---|
| 店铺客服 | 投诉、涉假、赔付、情绪激烈 | 店家客服（建工单） |
| 平台规则助手 | 查本店账号数据、涉诉讼/监管投诉 | 平台规则运营 |
| 治理规范助手 | 要求对在办案件下裁决 | 仲裁台（助手只给口径） |

「我的店被扣了 24 分，凭什么」这类问题必须拦：助手没有账号数据，
让它答就等于让它编一个分数。但拦住之后要给出口——处罚明细在「纠纷中心」，
不服可在生效后 7 天内申诉。只拦不给出路，用户只会换个渠道骂。

### 助手说的分数必须等于系统判的分数

规则库 21 条、规范库 20 条，答案里写的"扣 X 分"全部能对应到
`service/gov.py` 的 `DTYPES` / `NODES`。这不是巧合，是硬约束：

- FAQ 的数值照条款表写（`data/faq_rule.json`、`data/faq_gov.json`）
- 大模型拿到的上下文由 `_rule_digest()` 从同一张表生成
- `tests/board_e2e.py` 有一条用例把所有"X 分"抠出来，和 `/api/gov/meta` 比对

如果助手说"售假扣 12 分"、系统判 24 分，这个助手不是帮忙，是在制造投诉。

### 板块外观和动作也必须由服务端下发

`GET /api/cs/board` 现在返回一个 `ui` 对象：头像、徽标、引导语、状态文案、
输入框提示、**头部按钮列表**、以及 `can_escalate`。

这不是重构癖。原来这套东西写在前端 `SKIN` 里、按钮写在一串 `if/else` 里，
后果是三条一起犯：

- 动作分支漏了 `else` 的边界，治理板块落进了买家那一支——**运营在治理窗口
  右上角看到「平台介入」**，点下去是替别人投诉。用户一眼就看出来"板块没分开"。
- 状态栏在收到消息后被写回硬编码的「机器人 · 秒回」，治理板块的「规范库 · 在线」
  只活到第一条消息。
- 引导语只在"消息签名变化"时重绘，而新会话的签名和初始值都是空串，于是
  **引导语永远不出现**，窗口是一块白板。

现在前端只做渲染：`paintActions(ui.actions)` 遍历服务端给的动作，
`escalate` 类型才会生成 `#phEscalate` 这个节点；其他板块连节点都不存在，
不是"藏起来"。状态文案取 `ui.states[status]`，引导语取 `ui.greet`。

一条约束值得单独记：**「平台介入」只有买家看得到**。商家点它是投诉自己，
运营点它是替别人投诉；连运营用 `?scope=shop` 预览买家窗口时也不给——
预览看到的是"买家会看到什么"，而买家只有一种角色。

同一条约束也补到了纠纷中心：右上角那个「申请平台介入」以前对四种角色都显示，
运营看到的是"替别人投诉"的按钮。现在它默认 `display:none`，只有买家进页面时
才放开；商家/运营进去看到的引导语是"从左侧选一条纠纷查看证据、双方陈述与裁决"。

### 带单核查：治理板块的第三个入口

治理助手回答"条款怎么规定"，但不回答"这一单该不该罚"。两者之间还差一步：
**把这一单的事实摆出来**。这一步以前完全没有，运营想问某张单只能自己去仲裁台翻。

现在 `GET /api/cs/cases` 给候选案件（在办优先，已裁决的排后面供复核），
选中后 `POST /api/cs/sessions/{sid}/case` 返回一段拼装文本：

```
【案件】DP202610300003 · 假冒商品 · 待裁决
【双方】店铺：梦境数码专营店 / 买家：李澈
【订单】SO20261030005003 · 无线蓝牙耳机 Pro（白色/主动降噪版） · 1 件 × ¥899.00
【时间】付款 10-21 09:31 → 发货 10-21 23:31 → 签收 10-24 09:31
【物流】中通快递 · 运单 ZT028694460 · 揽收 10-22 03:31（发货后 4.0 小时）
【适用条款】《商家违规行为管理规则》3.1：售假…每次扣 24 分…
【口径】以上为事实与条款原文，本板块不替仲裁员下结论。
【下一步】裁决在「仲裁台」完成；需要商家答辩或补证的，在纠纷详情里发起。
```

三个刻意的选择：

1. **不用大模型。** 事实来自订单时间戳（`gov.order_detail()`），条款来自
   `t_clause` 原文，都是可核验的字符串；拼装不需要推理，也就不存在幻觉。
2. **最后两行必须是"不给结论 + 下一步去哪"。** 少了这句，运营会把条款堆叠
   直接复制进裁决书，一次口头结论就会被截图当依据。
3. **链路追踪面板单独画一格。** 它不走四级漏斗，硬套会显示"四层全跳过"，
   看起来像什么都没做——比不显示更误导。

顺带修了一个数据问题：订单的 `category` 是造数时随手写的，和店铺卖什么无关，
于是出现过"梦境数码的订单里是一件霞光实木边几"。现在商品按**店铺类目**推，
`backfill_order_items()` 会把已挂纠纷的那几张单纠正过来（只碰纠纷关联的订单，
不动历史订单池，可重复执行）。

### 治理板块顺带把三方接进来

运营进咨询窗口，第一眼要知道的不是"知识库多少条"，而是"有多少事卡在谁那里"。
所以 `gov` 板块右侧多一块：待受理/待裁决、商家未答辩、受限/停业店铺、待复核申诉，
每个数字都是一个入口（仲裁台 / 纠纷中心 / 客服会话）。
数字全部实时查库，不是页面自己数的。

### 分域之后还有一个维度：这是哪家店的话

分域解决的是「谁在问」，没解决「问的是哪家店」。v8 之前 74 条买家知识全局共享，
两家店问「什么时候发货」拿到同一个答案——霞光家居明明写着"大件 3-5 天备货"，
买家听到的却是平台的"48 小时出库"，然后拿这句话去投诉。**知识错了，话术越流利越糟。**

现在 `t_faq` 多一列 `shop_id`：

| `shop_id` | 含义 | 谁能维护 |
|---|---|---|
| `NULL` | 平台通用基线，全平台生效 | 平台运营 / 管理员 |
| `= N` | 第 N 家店的专属话术 | 该店商家本人 + 平台运营 |

检索时按 **店铺视野** 建索引：`平台通用 + 本店专属` 合并成一份，`(audience, shop_id)`
是索引的键。三个约束值得单独说，因为它们各自都踩过一次：

1. **同问法必须覆盖，不是"排第一就行"。** 本店和平台各有一条「什么时候发货」，
   BM25 分数会完全相等，靠 priority 只能决定谁排第一，平台那条仍留在候选里——
   大模型兜底时会把两套口径都读进去，然后混着说。所以 `rows_from_db()` 在
   建索引前就按归一化问法去重：本店说过的话，平台那条不进索引。
2. **缓存 key 必须带店铺。** 只带知识域的结果是：A 店买家问完，B 店买家问同一句，
   直接命中 A 店的承诺。`rr:cs:v{版本}:a{域}:s{店}:q:{md5}` 四个维度缺一不可，
   和"缓存不带规则版本号"是同一类故障。
3. **规则域、治理域不挂店。** 平台规则是统一口径，商家改一个字，全平台商家
   看到的都是错的。所以 `_resolve_shop()` 对非 `buyer` 域一律返回 `NULL`，
   接口层强制，不靠前端自觉。

配套的三处界面调整：

- 快捷问题从 `faq.rows_from_db(audience, shop_id)` 生成，和检索用同一份合并结果，
  「点下去必须命中」这条约束在分店之后依然成立；咨询窗口副标题直接写
  "知识：本店专属 N 条 + 平台通用 M 条"，商家改完能立刻看见数变了。
- 知识库表格多一列「归属」，商家看到的平台通用条目是**只读**的，按钮变成
  「改本店口径」——点开是复制一份本店专属条目，而不是回一个 403 让人无从下手。
- 阈值调试器按店铺打分。分店之后"同一句话在 A 店命中、B 店不命中"是正常现象，
  没有这个工具，运营只会以为知识库坏了。

**为什么不让商家直接改平台条目？** 那不是"权限小气"。74 条通用话术是 5000 家店的
共同基线，改一个字影响的是所有店铺的买家；而商家真正想说的是"我这家店的承诺"，
这两件事必须分开存，否则永远说不清"这句话是谁说的"。

## 三、核心难点：0.88 这个阈值到底在衡量什么

`sim ≥ 0.88` 听起来很明确，但 BM25 的原始分是无界的——它取决于查询长度、
文档平均长度、IDF 分布。直接把原始分和一个固定数比，等于拿体温计的刻度
去量身高：数值能算出来，但没有意义。

**做法是把分数归一化到一个有语义的量**：

```
sim = 0.55 × coverage + 0.45 × saturation
```

- `coverage`：查询词的 IDF 覆盖比例。买家问的实词有几个在 FAQ 里出现过。
  用 IDF 而不是词数，是因为"发货""退款"这种词的区分度远高于"我""的""吗"。
- `saturation`：带长度惩罚的 BM25 强度，除以"理想情况"分数（查询词各命中一次、
  文档长度等于平均长度）。衡量命中的**稠密程度**，而不是命中几个词。

0.55 / 0.45 的权重是调出来的：只看向 coverage，长问句会被短 FAQ 骗到高分
（"我要退款"→ 命中 100%，但它其实没说是哪个订单）；只看向 saturation，
短查询会被长 FAQ 淹没。

### 三次翻车，都发生在这个阈值上

**第一次：同义词扩展词被算进分母。**
为了让"我要退款"能命中"怎么申请退款"，我把同义词扩展后的词也放进归一化分母。
结果标准问法本身的分数被稀释到 0.6 左右，阈值形同虚设。
→ 分母只用**原始查询词**，扩展词只参与命中、不参与归一化。

**第二次：短语包含关系没有补偿。**
"可以开发票吗"和"能开发票吗"分词边界不同，纯词袋会低估这类完全同义的改写。
→ 加了 `PHRASE_BONUS`：归一化问句与 FAQ 问法互相包含时补 0.06。

**第三次：靠堆别名治不好语气词。**
"能不能便宜点"一直不命中，原因是 `能不能` 没被剥掉，导致覆盖率被拉低。
第一反应是往别名表里加一条——但那是治症状。真正的病在归一化：
礼貌语/语气词前缀应该在**进分词之前**剥掉。
→ `_POLITE` 正则循环剥离（`亲|你好|请问|我想问一下|能不能…`），
剥到不再变化为止。

现在的结果（实测，阈值 0.88）：

| 集合 | 结果 | 说明 |
|---|---|---|
| 标准 / 近似问法 20 条 | 命中 19，命中最低分 **0.960** | 直出 |
| 无关问题 9 条 | 9 条全部正确拒绝，最高分 **0.318** | 离阈值很远 |

漏掉的那条是「我的退款什么时候到账」（0.718）——它该命中「退款多久到账」，
但句首的「我的」没有被剥离，把覆盖率拉了下来。这条如实留着：
**它是归一化还没覆盖到的一类（人称/所属前缀），不是阈值设错了。**

**这是我最想强调的一点：阈值能不能用，取决于它两侧有没有"安全带"。**
0.88 之上全部 ≥ 0.96，之下最高只有 0.32，中间几乎是空的——说明这个阈值是
"选出来的"而不是"凑出来的"。如果分数密集分布在 0.85~0.90，那这个阈值
迟早会在某次数据更新后把正确答案挡在门外。所以真正该盯的不是阈值本身，
而是**两侧的间隔**。

## 四、Redis 那一层不只是"更快"

缓存的 key 设计决定了它会不会返回过期答案：

```
rr:cs:v{知识库版本}:q:{md5(归一化问句)}
```

- **知识库版本**：运营改一条 FAQ，版本号 +1，旧缓存自然失效。
  少了这一段，运营改完答案发现线上没变，会以为系统坏了。
  这是客服缓存和规则问答缓存最关键的差别——规则库几乎不动，
  而 FAQ 是运营天天改的活数据。
- **归一化问句**：`发货了吗？` 和 `发货了吗` 必须是同一个 key。

（规则问答那层还有一个 `rr:v5:faq:{模型名}:{md5}`，因为大模型换了措辞会变；
客服这层的答案是人类写死的，不需要跟模型名绑定。）

Redis 挂了怎么办：`cache.RC` 为 None 时全部降级到进程内 LRU，
功能不受影响，只是多实例之间不再共享。

## 五、转人工不是"答不上来才转"

只有"低置信"才转人工的客服系统，会在最该转的时候不转。`FORCE_HANDOFF`
用正则做硬拦截，命中即转，**不由分数决定**：

| 触发 | 正则示例 | 理由 |
|---|---|---|
| `user_request` 主动要求 | 转人工 / 人工客服 / 真人 | 用户说了算，不要试图挽留 |
| `complaint` 投诉维权 | 投诉 / 12315 / 起诉 / 曝光 | 机器人越解释越激化 |
| `fraud` 涉假涉诈 | 假货 / 诈骗 / 三无 | 禁止机器人对涉假表态 |
| `compensation` 赔付诉求 | 赔偿 / 三倍 / 精神损失 | 承诺了就是法律风险 |
| `abuse` 情绪激烈 | 垃圾店 / 黑店 / 滚 | 这时候讲规则等于火上浇油 |

之后才是分数级的 `low_conf`、`llm_unavailable`、`llm_uncertain`、`llm_handoff`。
工单优先级也跟着走：`complaint` / `fraud` 是 9，其余 7，`shop_suspended` 是 8。

转人工后会话进入 `status=agent`，机器人**闭嘴**——不是"优先级降低"，
是这个会话里它不再生成任何回复。坐席接管、回复、关闭后交还。

## 六、知识沉淀：让人工投入产生复利

坐席回答完一个问题，系统会把「买家问句 + 人工回复」抽出来提示沉淀为 FAQ。

这是整套系统里唯一能让成本递减的环节：
今天坐席回了 20 条知识库里没有的问题，明天这 20 条就该由机器人来答。
没有这一步，客服系统永远只有"消耗人工"，没有"减少人工"。

**踩过的坑**：第一版把"在吗"这种寒暄也当成问题沉淀了，配上了一句人工回复，
于是知识库里多了一条「在吗 → 支持七天无理由退货」，从此机器人对任何"在吗"
都回一段退货政策。

现在抓的是**最后一轮「买家问 → 人工答」**，并且往前回溯时跳过寒暄和过短的消息
（`GREETING` 集合 + 长度 ≥ 5 字）：

```python
if len(cand) >= 5 and cand not in GREETING:   # "在吗""你好""hi" 全部跳过
```

**已知缺口**：沉淀时没有做相似度去重，坐席把同一个问题答两遍就会多两条近义 FAQ。
正确做法是入库前先跑一次 `faq.search(q)`，最高分超过 0.75 就提示"疑似已有条目"，
而不是直接写。

## 七、和平台监管的联动

被平台停业/清退的店铺，客服入口直接拦住：

```python
st = gov.shop_status(sess["shop_id"])
if st in ("suspended", "closed"):
    # 不是静默失败，而是告诉买家"这家店被停业了，请走平台介入"
    return {"reply": tip, "source": "rule", "handoff": True, ...}
```

这一条很重要：如果只是不让商家登录，买家还会继续对着一个死掉的客服窗口说话。

### 会话 → 平台介入：这条进线必须能走通

机器人答不了转人工，人工也解决不了呢？如果这时候还要让买家自己跑到「纠纷中心」
重新填一遍表单，前面十分钟就白聊了——而且平台拿到的是一段脱离上下文的诉求。

所以会话里直接开了出口：`POST /api/cs/sessions/{sid}/escalate`，
坐席工作台是「转平台介入」，买家咨询窗口是「平台介入」，同一个接口。

```python
def escalate(sid, user, dtype="", claim="", claim_amount=0, order_no="", ...):
    old = dispute_of(sid)
    if old and old["status"] != "closed":
        return {"exists": True, **old}          # 幂等：一个会话只对应一张未关闭的纠纷
    buyer = _buyer_of(sess, user)               # 优先会话绑定的 buyer_id
    text = transcript(sid)                      # 对话记录直接成为诉求原文
    dtype = dtype or guess_dtype(text)          # 只做预填，提交人可改
    ev = _auto_evidence(order_no)               # 只带平台自己能核验的：聊天记录 + 订单
    return gov.create(shop_id, dtype, ..., session_id=sid, buyer=buyer)
```

四条设计约束，都是踩过或预判过的坑：

1. **幂等**：`dispute_of(sid)` 先查未关闭的单，重复提交返回原单。坐席连点两次就是两单，
   平台要判两遍，商家被扣两次分。`gov.create()` 里也补了同一道闸（错误码 400），
   因为投诉表单同样能带 `session_id` 进来。
2. **身份不能猜**：买家取会话的 `buyer_id`；老会话没绑 `buyer_id` 时，只有买家自己发起
   才认他的 id，坐席代转只能记昵称——否则纠纷会落到客服头上。
3. **证据不凭空生成**：自动带入的只有「聊天记录」（会话确实存在）和「订单截图」
   （平台订单库可直接核验）。商品实拍、检测报告这类实物凭证必须真的上传过，
   否则等于帮买家造证据。
4. **入口收口**：转介后会话状态置 `escalated`，机器人改口指路纠纷中心，
   待处理工单自动关闭。不这么做，买家会在客服和纠纷两个入口各说一半，
   仲裁员看到的是两份残缺记录。

反向也要通：裁决、结案、申诉复核的结果统一经 `_notify_cs()` 推回来源会话
（`service/gov.py` 直接写 `t_cs_message`，因为 `cs` 依赖 `gov`，反向 import 会成环）。
买家在咨询窗口里能看到「平台裁决：商家责任，退货退款」，而不是永远停在一句「已转平台」。

## 八、指标

`/api/cs/metrics` 输出：

- `by_source`：四级来源分布（redis / faq / llm / template / human / rule）
- `auto_resolve_rate`：无需人工介入即解决的比例
- `faq_hit_rate`：第二级命中率，直接决定 token 成本
- `handoff_rate`：转人工率，直接决定人力成本

当前演示数据：自动解决率 47.8%，来源分布 `{faq: 8, redis: 3, rule: 7, template: 5}`。

## 十、还没做的

- 无多轮上下文：每句话独立打分，指代词（"这个""那个"）会丢。
- 无流式输出：坐席看到的是整段回复，不是逐字。
- 情绪识别靠关键词，不是分类模型。
- 知识库去重只有阈值建议，没有自动合并。
- 知识只有「平台通用 + 单店」两级：没有类目模板（同类目店铺批量下发）、没有多店继承，5000 家店时会很难维护。
- 沉淀/新建知识没有审核流：坐席点一下「沉淀」就直接进检索，没有第二个人看过。
- 带单核查只按纠纷类型取**一条**条款原文，没有条款全文检索（406 条只用上了 9 条）。
- **三个知识域靠人维护，没有从规则表自动生成 FAQ**：条款改了指分，FAQ 里的数字得手动跟着改，目前只有测试能发现不一致。
