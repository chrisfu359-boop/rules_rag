# 电商系统全流程拆解（解剖样本：macrozheng/mall + 真实平台规则）

> 用途：为 `rules_rag`（电商商家规则合规助手）建立业务底座。
> 原则：系统行为取自可查源码，规则条款取自平台公开规范原文，两者严格分开标注。

---

## 0. 为什么用 mall 当样本，以及它的边界

**样本**：macrozheng/mall，Spring Boot + MySQL + Redis + RabbitMQ + ES，Maven 多模块
（`mall-common` / `mall-mbg` / `mall-security` / `mall-admin` / `mall-search` / `mall-portal`），
JDK 17，Apache-2.0，有在线演示后台与移动端。

**它能提供什么**：一条完整、可验证的正向交易链路——购物车、下单、库存锁定、支付回调、
超时取消、发货、确认收货、退货申请。状态码、表结构、锁库存 SQL 都能在源码里查到，
面试被追问细节时经得起查。

**它缺什么**（必须说清，否则整体判断会偏）：

| 缺失 | 说明 | 影响 |
|---|---|---|
| 商家入驻 | 单商家 B2C，无入驻审核、无店铺资质 | 类目资质类规则无处落地 |
| 平台治理 | 无违规判定、无扣分、无处罚、无申诉 | 治理类规则完全缺失 |
| 保证金 | 无 | 罚没、冻结、预留金机制缺失 |
| 结算账期 | 只有后台"财务管理"框架 | 资金侧规则缺失 |
| 多商家分账 | 无 | 佣金、TP 代运营场景缺失 |

**结论**：正确姿态是「用 mall 拿系统怎么跑，用真实平台规则拿规则怎么改系统」。
在真实平台里，这两件事是同一个系统的两半——规则中心发规则，交易系统执行规则，
结算系统按规则卡钱。这也是本项目的立足点。

## 1. 五大业务域

| 域 | 职责 | 核心表 / 载体 | 方向 |
|---|---|---|---|
| 供给 | 商品、SKU、库存、类目 | `pms_product` / `pms_sku_stock` / 类目品牌属性 | 正向 |
| 交易 | 购物车、下单、支付 | `oms_cart_item` / `oms_order` / `oms_order_item` | 正向 |
| 履约 | 发货、运单、轨迹、确认收货 | `delivery_sn` / 三方轨迹 / `confirm_overtime` | 正向 |
| 售后 | 退款、退货、换货、补寄、纠纷 | `oms_order_return_apply` / `oms_order_return_reason` | 逆向 |
| 资金 | 在途、结算账期、保证金、罚没 | 担保资金池 / 结算单 / `deposit` `penalty` | 逆向+结算 |

**一条判断**：在这个行业里，逆向流程的代码量通常超过正向。正向是唯一路径，
逆向每一个分支都要对账、回补、追责。

## 2. 正向主链路（9 个环节）

| # | 环节 | 系统实际动作（mall 源码级） | 状态 | 主要失败支路 | 规则落点 |
|---|---|---|---|---|---|
| 1 | 浏览加购 | SPU 选规格 → 对应 SKU → 写 `oms_cart_item` | — | 下架、无库存、地区不可售 | 类目资质、极限词、价格标示 |
| 2 | 结算页 | 按 SPU 分组算促销（单品/满减/折扣）+ 券 + 积分 + 运费 + 地址 | — | 券失效、地址不可达 | 满减叠加、包邮门槛、偏远地区 |
| 3 | 提交订单 | 校验 → 锁库存 → 18 位单号（Redis 自增）→ 落 `oms_order`/`oms_order_item` → 清购物车 → 发 RabbitMQ 延迟消息 | 待付款 0 | `lock_stock + qty <= stock` 条件更新失败 | 限购、预售、定金 |
| 4 | 支付回调 | 改状态 → 记支付时间与方式 → `lock_stock` 与 `stock` 同减 → 撤销延迟消息 | 待发货 1 | 重复回调（需幂等）、金额不符 | 支付方式、分期、货到付款 |
| 5 | 审单发货 | 打单拣货、回填运单号 | 已发货 2 | 超时未发、虚假发货 | 发货时效、虚假发货判定 |
| 6 | 在途 | 第三方物流轨迹回传 | 已发货 2 | 揽收超时、丢件、地址异常 | 物流异常认定、延迟赔付 |
| 7 | 确认收货 | 买家手动确认，或 `confirm_overtime` 天自动确认 | 已完成 3 | — | 自动收货天数（平台可改） |
| 8 | 售后 | 五种类型分流，商家审核 | 售后中 | **超时未处理＝默认同意** | 各类时限、凭证要求、判责 |
| 9 | 结算 | 账期到期 → 可提现 → 打款 | 完成 | 违规冻结、保证金不足 | 账期天数、扣分延长、罚没 |

### 2.1 订单状态码（mall 源码）

```
0 待付款   1 待发货   2 已发货   3 已完成   4 已关闭   5 无效订单
支付方式：0 未支付   1 支付宝   2 微信支付
```

主链路：`0 → 1 → 2 → 3`
旁路一：`0 → 4`（超时未付 / 主动取消）
旁路二：`3 → 5`（售后终态；mall 为教学简化，生产环境远复杂于此）

### 2.2 订单快照：为什么 `oms_order_item` 要冗余商品名与价格

订单是有法律效力的交易凭证，商品信息与金额必须定格在成交瞬间。
若只存 `product_id` 实时关联，商家改价、改名、下架后，历史订单会显示错误数据，
导致对账异常与纠纷。**这是电商系统的标准范式，不是冗余设计失误。**

### 2.3 库存三阶段（`pms_sku_stock`）

字段：`stock`（总库存）、`lock_stock`（已下单未付款）
可用库存 = `stock - lock_stock`

| 阶段 | SQL 语义 | 效果 |
|---|---|---|
| 下单 | `lock_stock + qty`，条件 `lock_stock + qty <= stock` | 预占，不动总库存 |
| 支付 | `lock_stock - qty` 且 `stock - qty` | 预占转实耗 |
| 取消 | `lock_stock - qty`，条件 `lock_stock - qty >= 0` | 释放回可售 |

**已知坑**：下单侧若不做显式校验，安全性就依赖状态机防重。延迟消息若重复投递，
取消执行两次会把库存"多释放"，这是超卖的反向错误（虚假可售）。
→ **延迟消息必须配幂等键。**

### 2.4 单号与超时

- 单号：`yyyyMMdd` + 来源（2 位）+ 支付方式（2 位）+ Redis 自增序列，共 18 位
- 超时参数集中在 `oms_order_setting`：
  `flash_order_overtime`（秒杀超时，分）/ `normal_order_overtime`（普通超时，分）/
  `confirm_overtime`（发货后自动确认收货，天）/ `finish_overtime`（自动完成交易，天）/
  `comment_overtime`（自动好评，天）/ `member_level`（适用会员等级）

**注意**：这是一张配置表，不是代码常量。真实平台上，这张表的值会被平台规则改写（见 §5）。

## 3. 逆向：五种售后类型

数据来源：抖音电商《商家售后服务管理规范》（公示修订版）2.3.1 条。

| 售后类型 | 触发时点 | 商家审核时限 | 后续时限 | 超时后果 | 库存动作 |
|---|---|---|---|---|---|
| 发货前退款 | 付款后未发货 | **24 小时** | — | 系统默认同意 | 释放锁库存 |
| 已发货退款（仅退款） | 已发货 | **36 小时** | 需拦截或召回 | 系统默认同意 | 拦截成功才释放 |
| 退货退款 | 签收后 | **36 小时** | 买家 7 天内寄回；签收起 48 小时（极速退款 72 小时）内退款 | 系统默认同意 | 收货验收后回补 |
| 换货 | 签收后 | **36 小时** | 7 天内发出并回填运单；签收起 48 小时 | 系统默认同意 | **提交申请即扣库存**，售后单关闭回补 |
| 补寄 / 维修 | 少件、破损 | **36 小时** | 按约定寄出 | 系统默认同意 | 补寄扣库存 |

### 3.1 三个易忽略点

1. **换货在申请提交时就扣库存**，不是等发货。目的是防止商家接了换货单却发不出货。
   → 售后的库存占用是独立于订单库存的第二条账。
2. **消费者寄回时限 7 天**，逾期视为未处理，但售后有效期内仍可重新提交。
3. **撤销与退款**：商家处理前消费者可撤销；商家同意退款后，系统自动原路退回。

### 3.2 mall 的售后模型（对照用）

`oms_order_return_apply.status`：`0 待处理 / 1 退货中 / 2 已完成 / 3 已拒绝`
`oms_order_return_reason`：退货原因字典（可启停、可排序）

对比可见：mall 只做了"退货退款"一种类型，且状态只有四态。
真实平台的五种类型 + 多段时限 + 超时默认同意，是教学实现里完全没有的部分。

## 4. 资金链路与规则截断点

主路径：`买家付款 → 平台担保在途 → 确认收货 → 结算账期 → 可提现 → 打款`

### 4.1 结算账期（抖音电商《商家货款结算日期细则》）

| 商家类型 | 适用类目 | 账期 |
|---|---|---|
| 非 0 元入驻 | 售后期 ≤ 30 天 | 确认收货后 **3 天** |
| 非 0 元入驻 | 售后期 > 30 天 | 确认收货后 **10 天** |
| 0 元入驻 | 全部 | 确认收货后 **21 天** |
| 即时零售·普通 | — | 3 天 |
| 即时零售·成人计生 | — | 7 天 |
| 即时零售·药店/医疗器械 | — | 10 天 |

规则原文明确：**实际以「抖店-资金-账单管理-待结算订单」页面展示为准。**
→ 这解释了为什么"规则文字"和"系统显示"必须一起给，只给规则会答错。

### 4.2 三类资金截断（快手《结算周期管理规则》，2026-10-08 修订）

| 触发条件 | 平台措施 |
|---|---|
| 资损风险（保证金低于阈值、退货补运费欠费、违约单待缴） | 暂停结算、延长结算周期、限制提现、冻结预留金 |
| 消费者/平台资损风险（刷单、套利、虚假发货、集中纠纷） | **延长自动确认收货时间**、**取消自动确认收货功能**、延长账期、暂停结算、限制提现 |
| 主体资质失效 | 暂停结算、延长账期、限制提现 |

### 4.3 违规扣分直接改账期（淘宝）

| 处罚分值 | 资金后果 |
|---|---|
| 2 分（含账期延长） | 被处罚商品下的在途订单，确认收货后延迟到账 **15 天** |
| 24 分 | 全店在途订单延迟到账 **30 天** |
| 48 分 | 全店在途订单延迟到账 **60 天** |
| 假货扣 24 分以上 | 还需支付违约金，从保证金扣除 |

渠道入驻另有扣分门槛（如全球购：近 90 天 A 类未达 12 分、近 365 天 B 类未达 12 分、无 C 类扣分）。

## 5. 三个反直觉机制（本项目最该讲的部分）

### 5.1 状态机里有"沉默分支"

售后五类时限的后半句全是"超时未处理，系统默认商家同意"。
商家问"买家申请退款我没理，会被罚吗"，正确答案不是"会罚"，而是
**"平台已视为你同意，款已退，你可能还不知道"**。

系统不是等商家点同意，是等商家不说话。

### 5.2 平台能远程修改你系统里的参数

快手规则原文列出的措施包含"延长自动确认收货时间""取消自动确认收货功能"。
这意味着"已完成"这个状态何时到达，不完全由买卖双方决定。

**规则不只是给人看的文档，它是会写进系统配置表的值。**
（对应 mall 的 `oms_order_setting.confirm_overtime`）

### 5.3 违规的代价是现金流，不是罚款

扣分 → 账期延长 → 在途货款被压住 15/30/60 天。
商家最疼的不是扣分本身，是几十万货款动不了。
这条把「平台治理」与「资金结算」两个域打通，也是商家最愿意付费咨询的问题。

## 6. 状态 × 规则矩阵（知识库骨架）

这是本次拆解最重要的产出：**知识库不按文档组织，按状态机节点组织。**

### 6.1 为什么

商家的问题永远从某个具体状态出发：

- "我这个单**已经发货了**，买家申请**仅退款**，我能拒吗？"
  → 状态（已发货）+ 类型（仅退款）+ 角色（商家）
- "我**扣了 12 分**，钱什么时候能提？"
  → 事件（扣分）+ 诉求（资金）

按文档切块只会召回《仅退款规则》总则，答不到"已发货"这个分支。

### 6.2 chunk metadata 规范

```json
{
  "scene": "aftersale.only_refund.shipped",
  "state_in": "已发货",
  "actor": "merchant",
  "timeout_hours": 36,
  "on_timeout": "auto_agree",
  "source_clause": "商家售后服务管理规范 2.3.1(二)",
  "effective_from": "2026-XX-XX",
  "category": null,
  "risk_level": "high"
}
```

检索策略：**先用 `scene` + `state_in` + `actor` 做标量过滤，再做向量召回。**
与设计总纲 §"先过滤再召回"同一原则，过滤键从「类目/时效」扩展到「业务状态」。

### 6.3 矩阵（首批 12 个场景）

| scene | 入口状态 | 角色 | 商家真实问法 | 必须命中的条款 |
|---|---|---|---|---|
| `order.create.limit` | 加购/下单 | 商家 | 我能不能设限购 | 限购规则、预售规范 |
| `order.price.label` | 上架 | 商家 | 划线价怎么标不违规 | 价格标示规范、处罚档位 |
| `order.stock.oversell` | 下单 | 商家 | 超卖了怎么办 | 缺货违约、赔付标准 |
| `fulfill.ship.timeout` | 待发货 | 商家 | 48 小时没发会怎样 | 发货时效、延迟赔付 |
| `fulfill.ship.fake` | 待发货 | 商家 | 上传假单号算虚假发货吗 | 虚假发货判定 |
| `aftersale.only_refund.shipped` | 已发货 | 商家 | 已发货买家仅退款能拒吗 | 仅退款规则 36h 时限 |
| `aftersale.return_refund.review` | 签收后 | 商家 | 退货审核多久、超时会怎样 | 退货退款 2.3.1(二) |
| `aftersale.exchange.stock` | 签收后 | 商家 | 换货为什么要扣我库存 | 换货库存规则 |
| `aftersale.reject.evidence` | 售后中 | 商家 | 拒绝退款要什么凭证 | 拒绝举证要求 |
| `dispute.arbitrate` | 纠纷 | 商家 | 平台介入会怎么判 | 争议处理规则 |
| `fund.settle.cycle` | 已完成 | 商家 | 钱什么时候到账 | 结算账期细则 |
| `govern.penalty.point` | 违规 | 商家 | 扣 12 分影响什么 | 扣分节点→账期/权益/活动 |
| `govern.deposit.deduct` | 违规 | 商家 | 保证金会被扣吗 | 保证金管理规范 |

`risk_level = high` 的场景（处罚金额、法律定性、合同变更）一律只给条款原文 + 强制转人工。

## 7. 对 rules_rag 的 7 条设计要求

1. **知识库目录 = 状态机节点**，不是文档章节。切块单位是「场景」，不是「段落」。
2. **每个 chunk 必须回答"在什么状态下、谁在问、时限多久、超时会怎样"**，
   缺任一项，这个问题就答不完整。
3. **"超时默认同意"必须作为独立字段**（`on_timeout`），不能藏在正文里。
   这是商家最容易踩、后果最直接的一条。
4. **规则文字 + 系统显示 必须一起给**。平台规则原文多次写"以页面展示为准"，
   只引条文会误导。
5. **扣分与资金必须建立跨域关联**。问到"扣分影响什么"时，
   要能同时答出违规分值与账期天数两张表。
6. **售后场景需要独立的库存口径**（换货申请即占库存），
   不能复用订单库存的描述。
7. **拒答边界以"是否有明确条款"为准**。有条款给条款号 + 原文 + 时限；
   没有条款（如"平台会怎么裁量"）→ 直接说无明确依据，转人工。
