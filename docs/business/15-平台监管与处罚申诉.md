# 15 · 平台监管：纠纷仲裁、处罚与申诉

> 店铺客服解决的是"我问你答"，解决不了"我不服"。
> 买家对商家的处理不满意时，如果没有平台介入的出口，他只有两个选择：
> 忍，或者去 12315 / 黑猫 / 社交平台曝光。后者对一个平台是实打实的合规风险。
> 所以纠纷必须有一个**有约束力的第三方裁决**，而且裁决结果必须能落到商家身上
> （扣分、降权、停业），否则调解就是空话。

## 一、五级链路

```
① 规则匹配    ~0ms    纠纷类型 → 违规条款 → 扣分标准，全部查表，模型不参与
② AI 定责     ~10ms   证据完整性 + 金额 + 历史违规 → 责任判定 + 置信度 + 说理
③ AI 自动裁决  ~0ms   置信度 ≥ 0.80 且非严重违规 → 结案 + 自动生成处罚单
④ 人工仲裁     —      涉假/欺诈/人身安全/金额超 1000/证据不足 → 仲裁员裁决
⑤ 申诉复核     —      商家申诉处罚、双方申诉裁决 → AI 初审建议 + 人工终审
```

越靠前越便宜，越靠后越贵。设计目标和客服那层一样：**让绝大多数纠纷停在
最便宜的那一层，但把"贵"的那一层留给真正需要的案件**。

## 二、三条不能破的边界

### 1. 扣分不许由模型决定

处罚依据必须是条款库里**真实存在**的条款号和条款里**写明的分值**：

| 纠纷类型 | 条款 | 扣分 | 依据文件 |
|---|---|---|---|
| 商品质量问题 | 4.1 | 0（退货退款） | 商家售后服务管理规范 |
| 描述不符 / 虚假宣传 | 2.2 | 2 分 | 商家违规行为管理规则 |
| 发货 / 物流问题 | 2.4 | 0.5 分 | 商家违规行为管理规则 |
| 售后不履行 | 2.3 | 1 分 | 商家违规行为管理规则 |
| 假冒商品 | 3.1 | 24 分 + 下架 + 扣保证金 | 商家违规行为管理规则 |
| 欺诈 / 诱导站外交易 | 3.2 | 48 分 + 清退 | 商家违规行为管理规则 |
| 商品危及人身安全 | 3.3 | 48 分 + 清退 | 商家违规行为管理规则 |
| 服务态度 | — | 0（规则无此条款） | — |

`DTYPES` 就是这张表的代码形态。**模型只做两件事**：判断事实属于哪一类、
把说理写成人话。让模型"综合判断扣几分"，等于把行政处罚权交给一个会编造的
组件——申诉时无法自证，监管检查时无法解释。

写死还有个副作用是好的：**"服务态度"这一项规则库里没有扣分条款，就真的不扣分**。
系统宁可给一条 0 分的责任认定，也不去编一个标准。

### 2. AI 自动裁决只覆盖"低金额 + 一般违规"

```python
auto_ok = (type.auto and liability == "merchant"
           and conf >= 0.80 and amount <= 1000
           and severity != "critical")
```

涉假、欺诈、人身安全一律转人工；金额超 1000 一律转人工。
这不是能力问题，是责任问题：**错的代价不可逆**。
一个被错误清退的店铺，损失不是重跑一次推理能补回来的。

不满足自动裁决时，`gate` 会标明卡在哪一关，前端直接显示给仲裁员看：

| gate | 含义 |
|---|---|
| `critical` | 严重违规，必须人工 |
| `amount` | 金额超过自动裁决上限 |
| `evidence` | 证据不足，置信度封顶 0.45 |
| `low_conf` | 置信度未达 0.80 |

### 3. 处罚必须可回滚

申诉成功要能把扣分退回去、把店铺状态恢复，并且留下"谁、什么时候、
因为什么撤销的"记录。只能加不能减的处罚系统，迟早会把一家店误杀，
而且没人能证明是误杀。

## 三、置信度不是一个数，是一串可解释的加减项

模型给一个 `0.83`，仲裁员凭什么信？所以置信度必须能拆开：

```
基础                              0.60
+ 0.14  举证材料齐全
+ 0.08  低金额（≤200）
+ 0.06  同类纠纷少（≤1 次）
+ 0.04  关联到订单号
+ 0.03  关联到客服会话
- 0.05  同类纠纷频发（≥3 次）
- 0.10  店铺已在处罚中
- 0.30  严重违规必须人工
→ 证据不足时封顶 0.45
```

页面上直接显示这串 `conf_steps`。**这是"AI 辅助决策"和"AI 黑箱"的分界线**：
仲裁员看到的不是一个数字，而是一条可以逐项反驳的理由链。

## 四、扣分节点：一次违规只罚当罚之罪

《商家违规行为管理规则》4.2.1~4.2.4 的阶梯：

| 累计扣分 | 节点处罚 |
|---|---|
| 2 分 | 警告 |
| 12 分 | 限制参加营销活动 30 天 |
| 24 分 | 搜索降权 + 限制发布 7 天 |
| 48 分 | 店铺清退 |

**顺序必须从高到低遍历，只发越过的最高那一个节点。**
一次售假 24 分会同时越过 2 分和 12 分两个节点，如果每个节点都发一条处罚，
商家会因为一次违规同时被警告 + 限营销 + 降权——罚不当罪，申诉时一告一个准。

## 五、状态机：处罚动状态，认定不动状态

`t_shop_credit.status` 由**当前生效的处罚**推导，不是存一个字段到处改：

```python
if "close" in types:        status = "closed"
elif "suspend" in types:    status = "suspended"
elif "downgrade" in types:  status = "downgraded"
elif "warning" in types:    status = "warned"
else:                       status = "normal"
```

**踩过的坑**：一开始把"认定商家有责但不扣分"（比如服务态度）也写成了一条
`warning` 处罚单，结果这家店永久停在"已警告"状态，而且永远摘不掉——
因为那条记录没法定"到期"，撤销它又没有理由。
现在这类记录用 `ptype='record'`，进 `STATUS_PENALTIES` 之外的集合：
**它是留痕，不是处罚**。

## 六、撤销要连带撤销

撤销一张扣分单后，由它触发的节点处罚（比如"累计满 2 分 → 警告"）还在生效，
店铺状态就恢复不了。

```python
# revoke 时：撤销扣分单 → 重算累计分 → 撤销已不成立的节点处罚 → 重算状态
cascaded = [p for p in 该纠纷的节点处罚 if 重算后不再越过该节点]
```

这条是 `tests/gov_e2e.py` 里专门盯的用例：撤销后店铺从 `suspended` 回到 `downgraded`
再到 `normal`，且 `t_penalty` 里保留全部历史（`status='revoked'`，不删行）。

## 七、申诉：AI 初审只给建议，不替人决定

```
商家提交申诉（7 天窗口，同一处罚只能申诉一次）
   → AI 初审：看有没有新证据、理由是否指向条款适用
   → 给出 accept / review / reject 建议 + 置信度 + 逐条理由
   → 人工终审：accept 才真正回滚
```

AI 初审的加减项：

```
+ 0.15  提交了新证据
+ 0.12  申诉理由指向条款适用争议
+ 0.10  原裁决为 AI 自动裁决（应容许人工复核）
+ 0.15  原裁决没有任何证据材料就下了结论
```

**踩过的坑：一个永远不成立的条件，等于一段死代码。**
"原裁决证据不完整"这一项原本写成：

```python
if d and _keys(d) and not evidence_of(d):   # ← 永远为 False
```

`_keys(d)` 非空意味着一件件证据都存在，那 `evidence_of(d)` 必然也非空；
两个条件互斥，这一分支从来没执行过。它不报错、不影响主流程，
只在"这条申诉该不该给 +0.15"上悄悄少了一个理由。

**凡是 `A and not f(A)` 形状的条件，都要停下来看一眼是不是写反了。**
后面统一成 `if d and not evidence_of(d)`：一件证据都没提交就下了裁决，
这种案子确实应该容许复核。

## 八、数据隔离：404 而不是 403

| 角色 | 能看到什么 |
|---|---|
| 买家 | 自己发起的纠纷 |
| 商家 | 自己被投诉的纠纷 + 自己的处罚与申诉 |
| 平台运营 / 管理员 | 全部 |

越权访问返回 **404 而不是 403**：403 等于告诉对方"这个 ID 存在，只是你不能看"，
本身就是信息泄露。这条和客服模块的会话隔离用的是同一套约定。

另外，**角色由服务端判定，不由前端传**：商家如果在请求里声称自己是"买家补充材料"，
就能绕开"商家答辩"的职责边界。所以 `as_role` 在服务端按 `shop_id` 和
`buyer_id` 算出来。

## 九、和客服模块的联动

停业 / 清退的店铺，客服入口直接拦住：

```python
st = gov.shop_status(shop_id)
if st in ("suspended", "closed"):
    # 不静默失败，而是明确告诉买家"这家店被停业了，请走平台介入"
    return {"reply": tip, "source": "rule", "handoff": True, ...}
```

只在登录处拦截是不够的：买家还会继续对着一个死掉的客服窗口说话，
然后去社交平台发一句"这家平台连客服都没有"。

### 进线打通：会话就是这个案子的第一份笔录

纠纷不能只从「买家自己跑去投诉」进来。真实平台的主干是：
**买家在客服窗口说不通 → 客服转平台 → 平台仲裁**。

`POST /api/cs/sessions/{sid}/escalate` 把这一步做成一次调用：
会话的 `shop_id` / `buyer_id` 直接成为纠纷的店铺和买家，`session_id` 落库，
对话记录成为诉求原文，`order_no` 一并挂上。坐席端叫「转平台介入」，
买家端叫「平台介入」，走的是同一套服务端逻辑，区别只在 `who` 记成谁提交的。

于是纠纷单里多了一条 `t_dispute.session_id`，仲裁台据此显示「来源客服会话」卡片：
买家最初那几句话、机器人怎么答的、客服接手后说了什么，全部摆在裁决表单上方。
这条数据 **只作陈述证据，不参与 `analyze()`** —— 否则一段措辞激烈的对话，
就能把责任判给商家。

结果也要回流：裁决、结案、申诉复核统一经 `_notify_cs()` 写回会话，
买家和商家在自己熟悉的窗口里就能看到结果，而不是靠平台打电话通知。

## 十一、角色与界面：四个角色，不是四套皮

「商家界面」和「平台界面」看起来像，是因为两边都是列表 + 详情 + 一堆表格。
但决定一个页面是什么的，不是配色和布局，而是**这个账号能看见谁的数据、能做什么操作**。
所以先把角色钉死，页面才有意义。

| 账号 | 角色 | 入口 | 能做什么 |
|---|---|---|---|
| 李澈 `lichen` | 买家 `buyer` | `/cs` 咨询窗口、`/dispute` 纠纷中心 | 选店铺咨询、发起投诉、补凭证、申诉裁决 |
| 冯霞 | 商家 `merchant` | `/app` 规则助手、`/service` 客服工作台、`/dispute` | 回复买家、答辩、看本店处罚与信用、申诉 |
| `ops` | 平台运营 `ops` | `/platform` 平台监管 | 受理投诉、仲裁、处罚、复审申诉、监管店铺 |
| `admin` | 系统管理员 `admin` | `/admin` 系统管理 | 账号、模型配置、审计日志 |

**管理后台不是平台方。** `admin` 是系统管理面（谁能登录、用哪个模型、操作有没有留痕），
`ops` 是业务裁决面（判谁有责、扣多少分）。两者权限不通用：管理员能改模型，
但不能替仲裁员下裁决；运营能裁决，但不能改系统配置。之前 `admin` 叫「管理后台」，
和「平台监管」只差两个字，看起来就像同一件事——现在改名为「系统管理」，
页面顶部也写明了这条边界。

**买家必须有独立账号。** 早期让商家兼职当买家，结果同一个账号既能答辩又能投诉，
三方角色在数据里根本分不开，「买家视角」只是换了套文案。现在 `t_cs_session.buyer_id`
绑定买家账号，坐席接口对 `buyer` 直接 403——以前 `_scope()` 对非商家一律返回 `None`，
等于「全平台可见」，买家登录后能翻到所有店铺的会话甚至接管。

### 平台案件工作台：三方对接

仲裁详情固定按这个顺序排，不是随便堆卡片：

1. **三方状态条** —— 买家提了什么、商家答没答辩、平台处在哪一步
2. **订单事实** —— 付款 / 发货 / 签收 / 售后申请四个时间戳 + 时效判定
3. **来源客服会话** —— 由会话转来的案子，摆出买家当时的原话（只作陈述证据）
4. **买家诉求与凭证**
5. **商家答辩**
6. **AI 定责 + 置信构成**
7. 处理过程、关联处罚、裁决表单

第 2 步是整个设计的关键：**纠纷必须挂订单号**。判「有没有超时」只能看订单时间戳，
不能看当事人自述——否则买家说「三天没发货」、商家说「当天就发了」，平台只能和稀泥。
`analyze()` 和页面读的是同一个 `order_detail()`，三方看到的时效结论完全一致；
买家端 `/dispute` 也显示同一张订单事实卡片，避免「平台看到了我不知道的证据」。
没有订单号的案子会明确标注「未关联订单」，提示仲裁员先补单号再裁。

#### 订单事实里到底要看什么（v8 补齐）

原先的 `t_order` 只有金额和四个时间戳。这带来两个具体问题，都不是"少个字段"那么轻：

- **判不了虚假发货。** 规则 2.4 写着"上传无效运单号的按虚假发货每次扣 4 分"，
  但订单表连运单号都没有，这条规则在系统里根本无法落地——所有发货类纠纷
  最多只能按"超时 0.5 分"处理，等于系统性地轻判。
- **说不清买的是什么。** 买家投诉"页面写实木、收到是塑料的"，订单上只有
  ¥268 这个数字，仲裁员无法确认这件商品就是详情页那件，举证方向都定不下来。

现在订单事实分三块，`order_detail()` 一次算完，买家端 `/dispute`、仲裁台、
客服转介三个入口读同一份：

| 块 | 字段 | 用途 |
|---|---|---|
| 商品 | `item_title` `sku` `qty` `unit_price` | 核对诉求指向哪件商品；`qty × unit_price` 与实付不一致时标红（有优惠/运费/部分退款，不能按实付全退） |
| 物流 | `carrier` `tracking_no` `picked_at` | 对得上承运商和单号；揽收时间是虚假发货的唯一可核验事实 |
| 时效 | `paid_at` `shipped_at` `received_at` `aftersale_applied_at` | 发货 48h / 售后 36h / 揽收 24h 三条 SLA |

虚假发货的判据写成一条明确的布尔值，而不是让 AI 自由发挥：

```
fake_ship = 已发货 and 未签收 and (无运单号 or 发货后 > 24h 仍无揽收记录)
```

这条判据同时影响两处，且必须一致：`order_detail()["fake_ship"]` 供页面显示，
`analyze()` 的 `shipping` 分支读同一个字段决定 4 分还是 0.5 分。没有它，
"商家点了一下发货按钮、物流公司根本没来取件"这种最常见的情形，
在系统里和"正常发货但物流慢"长得一模一样。

> 边界：已签收的不判虚假发货。包裹最终到了，就不属于"用虚假物流信息规避发货义务"。
> 这条边界不是技术细节——它是商家申诉时最先争的那句话。

#### 同一份事实的第二个读法：带单核查（v9）

仲裁台是"把案子判完"的地方，但运营更多时候只是想知道"这一单适用哪几条"。
以前治理窗口里唯一的入口是一句「这个案子怎么判」——没有指代对象，答不了，
必然被拦成转人工。现在治理板块提供「挑一单查条款」：

- `GET /api/cs/cases` 列出候选案件（在办优先，已裁决的排后面供复核申诉）
- 选中后 `POST /api/cs/sessions/{sid}/case` 返回**事实 + 条款原文**，最后一行
  永远是「本板块不替仲裁员下结论」

它读的是和仲裁台完全相同的两份数据：`order_detail()`（订单时间戳、商品、物流）
和 `t_clause`（条款原文）。区别只在**不产出 liability**——`analyze()` 才定责，
带单核查只把依据摆齐。这条分工必须写死，否则一次口头结论就会被截图当裁决书。

顺带修了一处数据可信度问题：订单的 `category` 原本是造数时随手写的，
和店铺卖什么无关，于是"梦境数码专营店"的订单里出现过一件"霞光实木边几"。
现在商品按**店铺类目**推（`_item_for()`），`backfill_order_items()` 只纠正
已经挂了纠纷的那几张单，不动历史订单池，可重复执行。带单核查里第一眼看到的
就是商品和店铺，这两者对不上，整张单就不可信了。

| 文件 | 角色 | 内容 |
|---|---|---|
| `web/cs.html` | 买家 | 选店铺咨询、机器人/人工切换、链路调试 |
| `web/dispute.html` | 买家 / 商家 | 订单事实、诉求与凭证、时间线、答辩、申诉 |
| `web/service.html` | 商家 / 运营 | 坐席工作台：会话队列、接管、回复、沉淀 FAQ |
| `web/platform.html` | 平台运营 | 看板、**仲裁台（三方对接）**、处罚与申诉、店铺监管 |
| `web/admin.html` | 系统管理员 | 用户、模型配置、审计日志（不参与裁决） |

仲裁台仍是左右分栏：左边是队列，右边是完整案卷。区别在于右边这份案卷是
「三方对齐过的事实 + 双方陈述」，而不是一堆只有平台自己能看懂的字段。

## 十二、验证

`tests/gov_e2e.py` —— 50 条用例，覆盖：


## 十三、还没做的

- 纠纷类型判定还是规则 + 关键词，没有做小样本分类。
- 检测报告等凭证没有 OCR 核验，只校验"有没有上传"。
- 没有处罚时效的自动到期任务（`suspend_until` 到期需要定时任务扫）。
- 商家信用分与搜索排序、流量分配还没有真正打通——现在只是状态位。
- 运单号是订单表里的静态字段，没接物流商接口：看不到实时轨迹，揽收时间是造数时写死的；
  真实系统应由物流回调写入 `picked_at`，而不是由我们填。
- 商品明细只有单行（`item_title`），多商品订单需要拆成 `t_order_item` 子表。
- 申诉窗口按提交时间算，没考虑举证期限中止。
