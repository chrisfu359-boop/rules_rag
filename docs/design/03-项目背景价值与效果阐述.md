# 03 · 项目背景 / 价值 / 效果 阐述

> 用途：简历项目描述 + 面试开场 3 分钟陈述。
> 纪律：**已验证的事实与预期指标严格分开**；所有数字必须带口径；未实测的指标一律写"目标口径"，建成实测后回填。

---

## 一、项目背景（为什么做）

### 业务背景（真实痛点）

1. **规则散、变、杂**。电商平台的经营规则散落在规则中心公告、类目细则、活动说明等几十个页面，大促节点前后高频变更。商家高频咨询集中在：退换货运费归属、违规扣分与账期影响、保证金、活动报名资质——这些问题的答案客服只能人工翻文档，响应慢且口径不一。
2. **知识过期比没有知识更危险**。新旧版本规则同时在网（如 2025 版与 2026 版细则并存），一般 RAG 系统会把已废止条款当现行规则答给商家，直接导致商家按错误规则经营、产生真实损失。
3. **答错的代价是钱和申诉**。商家拿到答案后要拿去申诉、去改经营动作，所以"意思大概对"不够——必须给条款号、给原文、给生效版本，否则不可用。

### 政策背景（立项抓手）

**GB/T 47746—2026《顾客联络服务 人工与智能客户服务协同要求》**，2026 年 9 月 1 日起实施。国标明确划线：

- 普通问答、产品介绍 → 允许 AI 自动应答；
- **价格、折扣、退款、赔偿、合同变更**等事项 → AI 只能"解释规则、收集材料、生成工单"，最终确认必须由人工或规范化流程完成；
- 人机切换时必须**同步客户信息、不重复询问**。

因此本项目不是"做一个问答 demo"，而是"**做一个符合国标的规则问答系统**"——合规条款直接转化为技术需求：风险分级、强制拒答、上下文交接、决策留痕。

### 一句话背景（面试开场用）

> 平台规则是商家的经营依据，但规则散落、高频变更、答错有真实资金代价。我在国标 GB/T 47746—2026 对 AI 客服划定的边界内，设计并实现了一个带时效感知、风险分级与强制引用溯源的电商规则合规问答系统。

### 目标用户群（按优先级四层）

| 层级 | 用户 | 画像与核心诉求 | 项目里的对应 |
|---|---|---|---|
| 核心 | 中小商家 | 1–10 人团队，无法务/规则研究员；问题高频重复，答案有明确条款依据，且等不起 | 问答主链路 + 条款引用溯源 |
| 协同 | 商家客服坐席 | 每天几十单咨询，需要秒级拿到带条款号的答案转述；答错规则导致投诉升级是 KPI 痛点 | 引用溯源 + 人工确认，契合国标"人机协同"定位 |
| 商业 | TP 代运营 / 客服 SaaS | 同时服务几十上百家店铺，最易触达的真实付费方；多平台规则汇总正是他们自己没能力维护的 | 多平台 metadata + 版本管理，知识库高复用 |
| 岗位 | 平台商家服务/治理团队 | 面试对口的岗位而非真实用户 | 风险分级 + 转人工 + 决策留痕 |

**边界说明（别说错用户）**：目标用户**不是消费者/买家**。消费者侧是交易咨询，高风险红线全在那里且大厂已有成熟系统；本项目差异化在**商家侧的经营规则**——数据散、变更频、大厂尚未做好。

**面试口径三句话**：主用户讲"中小商家 + 商家客服"；商业模式讲"TP/SaaS 复用"；岗位衔接讲"平台商家服务线"。

## 二、项目价值（解决什么、凭什么是我）

### 业务价值

| 价值点 | 说明 | 对应机制 |
|---|---|---|
| 降本 | 规则类咨询自动应答，减少人工翻文档与重复咨询 | L1/L2 轻量通道 + FAQ 快通道 |
| 合规 | 高风险事项（处罚金额、法律定性）绝不 AI 拍板 | L3 风险分级 + 强制转人工 |
| 可申诉 | 每个答案带条款号 + 原文 + 生效版本 | 条款级切分 + 引用校验 |
| 可信 | 规则变更后答案自动失效并回归验证 | 版本快照 + 变更检测 + 回归门禁 |

### 技术价值（区别于普通 RAG 的五个设计决策）

1. **先过滤，再召回**：`effective_from/to`、`category`、`platform`、`scene`、`state_in` 作为标量过滤在向量召回**之前**生效，失效条款与错类目条款根本不进候选集。（召回后过滤会出现"top20 过滤剩 1 条"的隐性故障。）
2. **规则三态**：`publish_date / effective_from / effective_to` 推导出"已公示未生效 / 生效中 / 已失效"三态。公示期的新规可以答"X 日开始执行"，但**不能当现行规则答**。
3. **按场景组织，不按文档组织**：chunk 携带 `scene / state_in / actor / timeout_hours / on_timeout`，因为商家提问永远带状态前提（"已发货的仅退款能不能拒"），按文档切块召回不到分支条款。
4. **失效版本不删**：存版本谱系而非最新文档——商家申诉要引用"当时适用"的条款。
5. **缓存 key 带规则库版本号**：规则一改版，旧答案全部自动失效，防止"缓存命中但答的是旧规"。

### 与已有项目集的协同（个人成长线）

- 短剧项目的**分层级联**（RF→FastText→BERT 按置信度分流）与本项目"轻量快通道 vs LLM 慢通道"是同一思想两次落地 → 简历主线："分层决策 + 成本闸门"。
- 短剧项目的**分层评测口径**（合成集 vs 真实语料分开报数）直接迁移为本项目的回归门禁方法论。

## 三、项目效果 / 成就

### 3.1 已完成、可现场验证（截至 2026-10-27）

| 事项 | 证据 |
|---|---|
| 完成领域调研与竞品排查 | 确认招投标等已拥挤赛道并排除；锁定电商规则合规这一差异化定位 |
| 完成数据源可行性实测 | 四大平台规则中心（淘宝/天猫/京东/抖店）均实测为 SPA，正文不可直接爬取 → 由此确立"法规层自动抓取 + 平台规则人工精选"的双层数据策略 |
| 完成系统侧知识建构 | 以开源 mall 系统源码为样本，产出九环节订单流程表、库存三阶段（lock_stock 条件更新）、售后五类型时限矩阵、资金链路规则截断点 |
| 完成架构设计定稿 | 三层风险分级（L1/L2/L3）、条款级切分方案、七字段 metadata schema、变更-回归-回流流水线，见 `00-设计总纲.md` |
| 完成基线代码复用评估 | 对 EduRAG 逐文件判定复用度（约 60% 骨架可复用），并识别出 4 处范式级不兼容与 2 处真实缺陷（父块去重丢失 metadata；BM25 softmax 阈值无物理意义） |

### 3.2 建成后的验收口径（目标，实测后回填）

评测集：**300 条**（法规条款 + 平台规则，每条含标准答案条款号与出处），按风险层级与场景分层。

| 指标 | 定义 | 目标 |
|---|---|---|
| 条款引用准确率 | 答案引用的条款号与标准答案一致的比例 | ≥ 90% |
| 时效正确率 | 答案引用条款处于正确版本（未引用已废止/未生效条款） | 100%（硬性） |
| 高风险漏答率 | 应转人工而未转的比例 | 0%（硬性） |
| 拒答精确率 | 主动拒答中确属高风险/无依据的比例 | ≥ 95% |
| P95 延迟 | 95 分位端到端耗时 | ≤ 3s（快通道 ≤ 500ms） |
| 单次成本 | 每次问答 token 成本 | 较全量 LLM 方案下降 ≥ 70% |

### 3.3 简历写法模板（建成后回填实测值）

> **电商规则合规问答系统（RAG）**｜独立开发｜Python / FastAPI / Milvus / BGE-M3
> - 面向电商商家规则咨询场景，构建"采集→条款级解析→时效/类目/场景过滤→风险分级→强制引用→转人工→变更回归"全链路，符合 GB/T 47746—2026 对 AI 客服的边界要求
> - 设计规则三态时效模型（公示/生效/失效）与"先过滤再召回"检索架构，杜绝引用废止条款；条款引用准确率 XX%，时效正确率 100%（300 条分层评测集）
> - L3 高风险事项强制转人工并带上下文交接，高风险漏答率 0%；答案 100% 附条款号与原文，支持商家申诉举证
> - 建立规则变更→自动回归→指标门禁流水线，规则库版本变更后缓存按版本失效，防止"知识过期比没有知识更危险"

### 3.4 面试追问预演

- **"和市面上的知识库问答有什么区别？"** → 一般 RAG 追求"意思对"，规则场景必须"条款号对、版本对"，正确性定义不同，倒逼切分粒度、metadata、过滤时序全部重构。
- **"为什么不直接用大模型？"** → 成本 + 时效 + 合规三重原因：单条几分钱 × 高频咨询；模型不知道规则哪天生效；国标要求高风险事项必须人工兜底。
- **"最难的部分？"** → 条款级切分：切分粒度必须等于引用粒度，字符切分做不到，这是范式问题不是调参问题。
