# 电商规则合规助手（RuleGuard）· 设计总纲

> 目标：一个**能按"上线系统"口径讲**的 RAG 项目，而不是又一个 RAG demo。
> 岗位对标：AI 应用开发 / 大模型应用开发（杭州·深圳优先，北京次之）
> 版本：v0.1 设计稿 · 2026-10-27

---

## 一、一句话定位

**面向中小电商商家的规则合规问答系统**：把散落在《电子商务法》《广告法》《消保法》《网络交易监督管理办法》与各平台规则中心里的条款，变成**带条款号引用、带风险分级、该转人工就转人工**的答案。

不做"通用问答机器人"。做的是**"商家敢照着执行的答案"**。

### 目标用户与代价

| 项 | 内容 |
|---|---|
| 用户 | 中小商家运营 / 客服，无专职法务 |
| 高频问题 | "生鲜能不能七天无理由""详情页写'全网最低'算不算极限词""虚假发货扣几分" |
| 答错的代价 | 罚款、下架、扣保证金、投诉成立 —— **有代价，所以拒答有意义** |
| 现状 | 规则散在几十个页面，大促前后高频变更，客服靠翻文档和问人 |

---

## 二、为什么这个项目算"能上线"

对照四条硬标准：

| 标准 | 本项目怎么满足 |
|---|---|
| 知识会变 | 法规有修订、平台规则周更；必须建**变更检测 → 增量重建 → 回归门禁**流水线 |
| 答错有代价 | 涉及处罚金额、法律定性；**风险分级 + 强制转人工**有国标依据 |
| 有客观 ground truth | 条款号是天然标注：一个问题对应第几条，可算准、可复核 |
| 城市有岗位 | 杭州（淘天、阿里国际、字节电商）、深圳（腾讯电商），规则/客服/合规方向密集 |

### 立意抓手：GB/T 47746—2026

《顾客联络服务 人工与智能客户服务协同要求》，**2026 年 9 月 1 日实施**（推荐性国家标准，非强制，讲的时候要说准）。

标准划的线，正好是本项目的技术需求：

- 普通问答、产品介绍 → AI 可自动回复
- 涉及**价格、折扣、退款、赔偿、合同变更** → AI 只能"解释规则、收集材料、生成工单"，**最终确认必须由人工或规范化流程完成**
- 人机切换要"提供便捷入口、衔接顺畅"，切换后**同步客户信息、不重复询问**
- 应保留显著 AI 生成标识与风险提示

> 面试价值：这不是"我想做个问答"，而是"**我要做一个符合国标的规则问答系统**"。合规要求直接翻译成了风险分级、强制拒答、上下文交接、决策留痕四个模块。

## 三、数据源：实测结论与方案

### 3.1 实测（2026-10-27）

| 数据源 | HTTP | 体积 | 正文可取 | 结论 |
|---|---|---|---|---|
| `rule.jd.com` | 200 | 3 KB | 否 | 纯 SPA，JS 渲染 |
| `rulechannel.taobao.com` | 200 | 1.7 KB | 否 | SPA |
| `school.jinritemai.com/doudian/web/rules` | 200 | 28 KB | 否 | 无中文正文 |
| `flk.npc.gov.cn` | 200 | 552 B | 否 | SPA，有 API 需逆向 |
| `samr.gov.cn`（市场监管总局） | 200 | 95 KB | **是** | 静态 HTML 可取 |

**结论：四大平台规则中心不能靠爬虫拿正文。** 这是本项目第一个设计约束，也决定了后面所有取舍。

### 3.2 采用方案：三层知识库

| 层 | 内容 | 获取方式 | 规模目标 |
|---|---|---|---|
| L1 法规层 | 电子商务法、广告法、消保法、网络交易监督管理办法、价格法、反不正当竞争法 | 官方公开文本，静态页可取 | 6 部，约 **500 条** |
| L2 平台规则层 | 淘宝/天猫、抖音电商、京东、拼多多的核心规则（处罚、发货、售后、内容） | **人工精选 + 记录来源 URL 与生效日期** | **80–150 条** |
| L3 类目细则层 | 生鲜、3C、服饰的差异化规则 | 同上 | 3 类目，约 **60 条** |

**为什么人工精选而不是爬全量：**

1. 平台规则爬不到正文（已实测）；
2. 更重要——**全量但无法标注 = 没有评测集 = 项目无法证明自己准**。200 条人工核对过的条款，能建 300 条评测集，能算出条款引用准确率；10 万条爬来的，只能讲"我知识库很大"。
3. "我逐条读过并标注了来源与生效期"这件事本身，就是数据工程能力，比爬虫更能打。

> 数据量不大（几 MB），但质量、可追溯性、可评测性全部满足。这是**故意做小**，不是做不到做大。

## 四、范围边界

### MVP 做（一个人 3–4 周）

- L1 全部 + L2 精选 80 条 + L3 三个类目
- 条款级切分 + metadata（含生效区间、类目、风险等级、来源 URL）
- 混合检索（稠密 + BM25）+ 时效过滤 + 类目过滤 + Reranker 精排
- 三级风险策略（直答 / 带免责答 / 转人工）
- 条款引用展示：条款号 + 原文片段 + 来源链接
- 300 条评测集 + 四项指标
- 规则变更检测 + 回归门禁（最小可用版）
- FastAPI + 单页前端

### MVP 不做（写进 README 的"未来工作"，面试主动讲）

- 全平台规则覆盖（做不到，也不必要）
- 多租户 SaaS、计费
- 商品详情页自动扫描（放 P2）
- 复杂 Agent 编排 / 多轮自主规划（放 P2）
- 用户体系与权限（答辩场景不需要，但要能说清怎么做）

## 五、架构

```
┌─ 采集层 ─────────────────────────────────────────┐
│ 法规静态页抓取 │ 规则人工录入(CSV) │ 变更探测(hash) │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ 加工层 ─────────────────────────────────────────┐
│ 条款级切分 → metadata 注入 → 人工校验 → 入库      │
│ (章/节/条/款/项 保留层级与条款号)                 │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ 存储层 ─────────────────────────────────────────┐
│ Milvus: 稠密+稀疏双向量 + 标量字段(过滤用)        │
│ MySQL : 条款原文 / 版本表 / 变更日志              │
│ Redis : 答案缓存(带规则版本号) / 热点条款          │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ 服务层 ─────────────────────────────────────────┐
│ 查询理解(改写/类目识别) → 过滤+混合召回 → 精排    │
│ → 风险分级 → 生成(强制引用) → 拒答/转人工         │
└──────────────────┬───────────────────────────────┘
                   ↓
┌─ 应用层 ─────────────────────────────────────────┐
│ Web 问答 │ 条款溯源页 │ 变更看板 │ 评测报告        │
└──────────────────────────────────────────────────┘
        横切：日志埋点 · 成本统计 · 回归门禁
```

**与 EduRAG 的关系**：复用的是流程骨架（FastAPI + Milvus + 混合检索 + Reranker + 流式），**不复用的是代码**。新增的是条款级切分、时效与类目过滤、风险分级、变更流水线 —— 这四块是原项目没有的，也是面试要讲的部分。

## 六、七个核心设计决策

### D1 · 条款级切分，不按 token 切

规则文本有天然层级：**法 → 章 → 节 → 条 → 款 → 项**。

- 一个 chunk = 一条（长条款按款拆，但保留所属条号）
- **禁止跨条合并**，即使两条都短
- 父块（整章）只用于提供上下文，不直接作为答案依据

理由：引用必须能落到"第X条第X款"。按 512 token 切出来的片段，无法告诉商家"你违反了哪一条"，答案就失去可执行性。

### D2 · metadata schema（本项目的技术核心）

```json
{
  "chunk_id": "adlaw_9_2",
  "doc_id": "adlaw",
  "doc_title": "中华人民共和国广告法",
  "doc_type": "law",              // law | platform_rule | category_rule
  "platform": null,               // taobao | douyin | jd | pdd | null
  "chapter": "第二章 广告内容准则",
  "article_no": "第九条",
  "paragraph_no": 2,
  "text": "广告不得有下列情形：……（三）使用“国家级”、“最高级”、“最佳”等用语；",
  "publish_date": "2021-01-22",   // 公示日：商家可见，但尚未生效
  "effective_from": "2021-04-29",
  "effective_to": null,           // null = 现行有效
  "category": null,               // null = 通用；否则 fresh_produce | digital | apparel
  "risk_level": "high",           // low | medium | high
  "source_url": "https://...",
  "content_hash": "sha256:..."
}
```

四个字段撑起四个能力：

| 字段 | 支撑的能力 |
|---|---|
| `effective_from/to` | **时效过滤**：只召回当前生效版本，杜绝"引用已废止条款" |
| `category` | **类目隔离**：生鲜规则不串到 3C |
| `risk_level` | **风险分级拒答**：high 一律转人工 |
| `content_hash` | **变更检测**：hash 变了就是规则变了 |

#### 为什么是「三态」而不是「有效/失效」两态

平台规则在生效前有公示期（商家听证），所以任一时刻规则库里有三种状态：

| 状态 | 判定条件 | 系统行为 |
|---|---|---|
| 已公示未生效 | `now < effective_from` | 可以答"新规将于 X 日执行"，**但不能作为当前执行依据** |
| 生效中 | `effective_from <= now < effective_to` | 默认检索范围 |
| 已失效 | `now >= effective_to` | 不参与检索，仅用于历史追溯与申诉举证 |

这个三态来自业务现实（公示期是平台治理的强制环节），不是为了设计而设计。**如果只做两态，系统会在公示期把新规当现行规则答给商家**——这是真实会出事故的场景。

同理，商家在申诉时要引用"当时适用"的条款，所以失效版本不能删，只能标记。

### D3 · 检索：先过滤，再混合召回，最后精排

```
query
 → 类目识别（用户选 or 模型判）
 → 标量过滤：默认只取「生效中」（effective_from <= now < effective_to）
              若查询意图是"最近有什么新规/什么时候执行"，改走「已公示未生效」态
              AND (category == 用户类目 OR category IS NULL)
              AND (platform == 用户平台 OR platform IS NULL)
 → 混合召回 top20（BGE-M3 稠密 + BM25 稀疏，WeightedRanker）
 → Reranker 精排 top5
 → 风险分级
 → 生成
```

**顺序不能反**：先过滤再召回，而不是召回后再过滤。因为失效条款和错类目条款会挤占 top-k 名额，先召回后过滤会导致"过滤完只剩 1 条"。

> 这个点面试很吃香：它说明你理解**过滤与召回的耦合关系**，而不是把 filter 当后处理。

### D4 · 三级风险策略（对应 GB/T 47746）

| 级别 | 触发条件 | 系统行为 |
|---|---|---|
| **L1 咨询** | 规则解释、流程说明（"七天无理由的起算时间"） | 直接答 + 引用条款 |
| **L2 判断** | 需要结合具体事实判断（"我这段文案算不算极限词"） | 答 + 明示"以平台判定为准" + 给自检清单 |
| **L3 高风险** | 涉及处罚金额、法律定性、合同变更、赔偿 | **不给结论**，只给条款原文 + 建议 + **强制转人工** |

关键区分：**拒答不是"答不出来"，是"按规则不该由我答"**。前者是能力缺陷，后者是合规设计。这个区别必须在面试里主动讲。

### D5 · 规则变更 → 增量重建 → 回归门禁

这是"上线"与"demo"的分界线，也是最有讲头的一块。

```
定时任务（每日/每周）
 → 重抓 source_url（静态页）或比对人工录入版本
 → 计算 content_hash
 → 若变化：
     ① 新规则先以「公示态」入库（publish_date = 今天，effective_from = 公示截止日）
     ② 旧版本写 effective_to = 新版本生效日（不删，保留历史以便申诉追溯）
     ③ 到生效日由定时任务自动切换状态，不依赖人工改数据
     ④ 触发回归测试：跑固定评测集
     ⑤ 指标下降超过阈值（如条款引用准确率 -3pp）→ 告警 + 阻断发布
     ⑥ 答案缓存按规则库版本号失效
```

**一个必须写进简历的点**：缓存 key 必须带规则版本号。否则规则更新后，用户还在拿到旧答案——这类 bug 在生产里极难排查，因为"缓存命中"看起来一切正常。

> 这条来自真实踩坑经验：缓存要么带版本，要么就别缓存。

### D6 · 评测集构造

300–500 条，每条包含：

| 字段 | 说明 |
|---|---|
| question | 商家真实问法（含口语、错别字、省略） |
| gold_article | 标准条款号（如"广告法第九条"） |
| key_points | 答案必须覆盖的要点（2–4 个） |
| risk_level | 期望的风险等级 |
| category | 类目 |
| source | 人工标注 / 从客服对话改写 |

分层报数，**绝不给单一"准确率"**：

| 分层 | 说明 | 为什么分层 |
|---|---|---|
| 法规类问题 | 答案在 L1 | 最简单，指标应最高 |
| 平台规则类 | 答案在 L2 | 中等 |
| 跨层冲突 | 法规与平台规则表述不一致 | **最难，也是最有价值的** |
| 高风险拒答 | 应触发 L3 | 单独算漏答率 |

### D7 · 四项指标（都能从日志算，不需要大规模标注）

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **条款引用准确率** | 引用的条款号 == gold_article 的比例 | 引用错了，答案再流畅也是错的 |
| **时效正确率** | 未引用 effective_to 已过期的条款 | 上线系统独有指标 |
| **拒答准确率** | 高风险该拒的拒了 / 不该拒的没拒 | 对应国标要求 |
| **答案忠实度** | 答案要点是否都能在检索到的条款里找到支撑 | 抗幻觉 |

辅助：P95 延迟、单次 token 成本、转人工率、首次解决率。

## 七、可观测与成本

每次请求记录一行结构化日志：

```
query, category, platform, 命中条款[], 召回耗时, rerank耗时,
生成tokens, 风险等级, 是否转人工, 引用条款号, 规则库版本号
```

由此可直接出：
- **成本看板**：单次成本 = (输入 tokens × 单价 + 输出 tokens × 单价)，按日聚合
- **质量看板**：引用准确率、拒答率的时间趋势（规则更新后是否劣化）
- **容量看板**：P50/P95 延迟、缓存命中率

> 大厂面试很少问"你怎么监控"，但答得出来的人和答不出来的人，差一个职级。

## 八、迭代路线

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P0**（3–4 周） | MVP：三层知识库 + 条款级切分 + 混合检索 + 风险分级 + 300 条评测 | 可演示系统 + 评测报告 |
| **P1**（+2 周） | 变更检测 + 回归门禁 + 缓存版本化 | "可上线"叙事成立 |
| **P2**（+2 周） | **商品文案合规自检**：输入详情页文案，主动扫出违规点并给条款依据 | 从"问答"升级为"检查"，有真实下游动作 |
| **P3**（可选） | **多平台规则对比**：同一问题，淘宝/抖音/京东答案不同 | 多知识域隔离的展示，商家多平台开店是真实场景 |

**P2 是真正的差异化**：问答是"人问它答"，自检是"它主动发现问题"。后者才叫下游有动作。

## 九、面试追问预演

**Q：为什么不用大模型直接答，非要搞 RAG？**
> 规则问题要的是"哪一条"，不是"大概意思"。大模型知道"极限词不能写"，但说不出"广告法第九条第（三）项"，商家的申诉材料里必须有条款号。而且法规会修订、平台规则周更，模型知识更新成本远高于更新索引。

**Q：你的知识库有多大？**
> 约 700 个条款 chunk（6 部法规 + 100 条平台规则 + 3 个类目细则）。**故意做小**——因为我要保证每一条都能人工核对来源与生效期，这样才有评测集。爬 10 万条但无法标注，项目就无法证明自己准。

**Q：怎么保证不引用已废止的条款？**
> 每条 chunk 带 effective_from/effective_to，检索时**先做标量过滤再召回**，失效条款根本不进候选集。另外缓存 key 带规则库版本号，规则更新后旧缓存自动失效。

**Q：涉及罚款的问题你怎么答？**
> 不答结论。按 GB/T 47746—2026 的要求，涉及价格、赔偿、合同变更这类事项，AI 只能解释规则和生成工单，最终确认必须由人工完成。所以这类问题我会给条款原文、给风险提示，然后转人工，并且把上下文一起带过去，不让用户重复描述。

**Q：这和普通客服机器人有什么区别？**
> 普通客服机器人目标是"少转人工"，本项目目标是"该转就转"。前者优化的是成本，后者优化的是**错误成本**。规则答错会导致罚款和下架，所以转人工率不是越低越好，而是要和漏答率一起看。

**Q：怎么评估效果？**
> 四项指标：条款引用准确率、时效正确率、拒答准确率、答案忠实度。分三层报数（法规/平台规则/跨层冲突），跨层冲突最难，指标会明显低一档——我会把三个数一起给，不给单一准确率。

**Q：规则更新了怎么办？**
> 内容 hash 变了就触发流水线：旧版标记失效日、新版入库、跑回归测试、指标掉超阈值就阻断发布。评测集是固定的，所以能判断"这次更新有没有让系统变差"。

## 十、已知风险与降级方案

| 风险 | 影响 | 降级方案 |
|---|---|---|
| 平台规则正文抓不到 | L2 数据量受限 | 已改为人工精选；必要时只做 L1 法规 + L3 类目，业务仍成立 |
| 法规条款存在修订版 | 时效错误 | 以官方最新版为准，保留历史版本表 |
| 评测集人工标注成本高 | 300 条需要 2–3 天 | 先做 150 条，够算指标即可；后续增量 |
| 类目识别不准 | 检索范围错 | 前端让用户显式选类目，模型只做默认值 |
| 生成模型幻觉引用 | 引用不存在条款 | 生成后校验：引用的条款号必须在本次召回集内，否则重生成或降级为"仅列条款" |

## 十一、面试时的一句话总结

> 我做了一个电商规则合规助手：把 6 部法规和 100 条平台规则做成条款级知识库，检索时按生效期和类目做前置过滤，答案必须带条款号引用。涉及处罚和赔偿的问题按国标强制转人工。配套 300 条评测集和规则变更回归门禁——因为规则每周都在变，没有回归测试的 RAG 系统不敢上线。
