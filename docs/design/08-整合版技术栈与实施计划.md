## 一、技术栈（左侧为设计，右侧为 Demo 实际跑通状态）

| 层 | 设计选型 | Demo 实际 | 状态 |
|---|---|---|---|
| 服务 | FastAPI + SSE | FastAPI 0.11x（Python 3.13） | ✅ 跑通 |
| 条款存储 | MySQL 8 | MySQL 8 @127.0.0.1:3307（root） | ✅ 283 条入库 |
| 检索-向量 | BGE-M3 + Milvus | **未接入**（本机 Python 3.13 无 torch，装 FlagEmbedding 需数 GB） | ⏳ 待装依赖 |
| 检索-词法 | MySQL BM25 / 全文索引 | **纯 Python BM25 + jieba**（283 条规模足够，延迟 &lt;10ms） | ✅ 跑通 |
| 缓存 | Redis（key 带版本） | Redis 6379（有密码），`rr:v2:faq:{md5}` | ✅ 命中 0–3ms |
| 查询理解 | 规则+轻量模型 | 纯规则：7 类场景 + L1/L2/L3 风险 | ✅ 跑通 |
| 生成 | LLM API | **未接 LLM**，答案由条款抽取 + 模板生成 | ⚠️ 抽取式 |
| 引用校验 | 条款号 ∈ 召回集 | 已实现（只校验生成结论，不校验原文） | ✅ 通过 |
| 评测 | 300 条分层集 | 7 条人工小测 + 4 条预设 | ⚠️ 待扩充 |

**为什么先不接向量**：Demo 的目标是验证"切分→过滤→召回→引用→转人工"这条链路是否成立。
283 条规模下 BM25 延迟 &lt;10ms，换向量只是提升召回质量，不改变链路结构。
接口 `search(query, top_k, scene)` 保持不变，接向量时替换实现即可。

## 三、Demo v0.1 实测结果（诚实版）

| 指标 | 实测 | 说明 |
|---|---|---|
| 条款数 | 283 | 4 部法律/规章 |
| 模拟订单 | 5,000 | 8 类店铺 · 6 种状态 · 7 类售后 |
| 端到端延迟 | 3–47 ms（P50≈6ms） | 无 LLM，纯检索+模板 |
| 缓存命中延迟 | 0–3 ms | Redis `rr:v2:faq:*` |
| 引用校验通过率 | 100%（4 预设 + 7 小测） | 条款号均在召回集内 |
| 预设场景 Top1 | 4/4 | L1 定义 / L2 时限 / L3 违规判定 / 订单上下文 |
| 自建 7 题小测 Top1 | **3/7** | 纯 BM25，难例上会跑偏 |
| 自建 7 题小测 Top3 | **5/7** | 经 rerank 后可用性会明显提升 |

**Top1 只有 3/7 这件事必须主动讲**，它正好说明两件事：
1. 纯词法检索对"口语化、术语换说法"的鲁棒性不足，向量召回 + reranker 是刚需（对应 docs/04 §3）；
2. 没有评测集就只能靠感觉，所以我把它写进报告而不是藏起来。

## 七、已知局限与两条备选路径

**局限（要在面试里主动说）**
1. 检索是词法通道，口语换说法会跑偏（Top1 3/7 已实测）；
2. 未接 LLM，答案是抽取式，语言不够自然，但引用 100% 可核；
3. 平台规则层缺失，涉及平台专属时限的问题只能拒答转人工；
4. 评测集只有 7 条人工小测，不足以支撑"准确率"这种表述。

**备选 A（稳妥）**：先补 P2 向量检索 + rerank，把 Top3 做到 85% 以上，再接 LLM。
**备选 B（快出效果）**：先接 LLM + 完善前端，把"能演示"做到最好，检索后续升级。
建议 A，因为检索不行，LLM 只会把错条款写得更像对的。

**平台规则的现实获取路径**（按可行性排序）
1. 平台官方帮助中心的部分静态页（非规则中心）；
2. 平台开放平台/服务商文档中的规则摘要；
3. 商家后台公告（需登录，只能人工）；
4. 公开的行业解读文章（**不可作为条款依据，只能用于发现问题**）。
结论不变：平台规则层要么人工录入，要么放弃，不要用二手解读冒充条款。
