# 04 · 技术架构设计（rules_rag 电商规则合规问答系统）

> 配套文档：00-设计总纲（业务与评测）、01-电商系统全流程拆解、02-EduRAG 复用评估、03-背景价值效果。
> 本文回答"系统怎么搭"：五层职责、三存储分工、两条数据流、内存预算。与架构图 `rules_rag技术架构总览` 对应。

---

## 0. 技术栈总览

| 组件 | 选型 | 在本系统的职责 | 选型理由 |
|---|---|---|---|
| **NLP-嵌入** | BGE-M3 | Query/条款双编码，**同时输出 dense + sparse 向量** | 一个模型支撑双向量混合检索，中文规则文本效果好 |
| **NLP-重排** | bge-reranker-base | 对融合后 top20 精排 | large 版 2.1G 在 15G 内存机器上会崩，base 损失约 1–2pp |
| **NLP-轻量分类** | 规则词表 + TF-IDF/线性模型（可升级 BERT-tiny） | 意图分类、场景/状态识别、风险预判 | 查询理解不能每个请求都过 LLM——沿用短剧项目"分层级联"思想 |
| **MySQL 8.0** | 单实例 | 条款源数据、版本谱系、变更日志、问答日志、评测集、人工反馈 | 结构化真相源；BM25 用其 ngram 全文索引 |
| **Milvus 2.x** | milvus-lite（嵌入式） | 条款向量检索 + **标量过滤**（时效/类目/场景/风险） | lite 无独立进程，省 ~2G 内存，适配本机约束 |
| **Redis 6** | 单实例 | FAQ 快通道缓存、embedding 缓存、会话上下文、分布式锁、限流 | 一切缓存 **key 必须带规则库版本号** |
| **LLM** | API 可配置（DeepSeek / 通义） | 仅 L2 慢通道生成答案 | 高频简单问题走 FAQ/条款直取，不烧 token |
| **服务** | FastAPI + SSE | 流式问答、管理接口 | 与短剧项目同栈，复用 service.py 启停经验 |
| **部署** | docker-compose（MySQL/Redis）+ Python 进程 ×2 | 单机 | 进程拆分见 §6 内存预算 |

## 1. 五层职责（对应架构图）

**① 接入服务层**
- `POST /api/query`（SSE 流式返回）、`POST /api/feedback`、管理端 `/api/admin/*`（规则录入、触发重建、触发回归）
- 鉴权（API Key 起步）+ 限流（Redis 滑动窗口）
- 会话上下文：Redis 存最近 N 轮 query 与已给条款号，供多轮追问与"不重复询问"

**② NLP 查询理解**（全部轻量模块，目标 <50ms）
- **意图分类**：规则咨询 / 活动咨询 / 闲聊 / 投诉（后者直接转人工）
- **场景/状态识别**：从 query 抽 `scene` / `state_in` / `actor`（"已发货…仅退款" → `aftersale.only_refund.shipped` + `merchant`）——这是检索标量过滤的核心输入
- **Query 改写**：口语→规则术语对齐（"钱什么时候能到账"→"结算账期"），词表映射 + 同义词典，不用 LLM
- **风险预判**：命中处罚金额/法律定性词表 → 直接判 L3，跳过检索生成

**③ 检索层**（本系统的核心竞争力，顺序不可变）
1. **Redis FAQ 快通道**：归一化 query 命中 → 校验版本号 → 直接返回（目标覆盖 30–40% 流量，P95 <500ms）
2. **Milvus 向量召回**：**先做标量过滤再算向量** —— `effective_from <= now < effective_to`（三态：只检"生效中"，"已公示未生效"单独标记）、`category`、`platform`、`scene`/`state_in`（可空通配）
3. **MySQL BM25**：ngram 全文索引兜底，接住型号/条款号/专有名词（向量对这些弱）
4. **RRF 融合 → reranker 精排** → top5 条款 + 父条款路径

**④ 生成与合规层**
- **风险路由**：L1 直答 / L2 生成+免责声明 / L3 只给条款原文+风险提示+强制转人工（带上下文交接，不重复询问）
- **Prompt 组装**：条款全文 + 条款号 + 生效期 + 平台名，指令要求"必须引用条款号，不得超出条款内容"
- **引用校验**（生成后硬校验）：答案中出现的每个条款号必须在召回集内，否则拦截重试一次 → 仍失败则降级为"仅条款原文"模式。**这是反幻觉的最后一道闸，不依赖模型自觉**
- 转人工工单：MySQL 落单 + 摘要 + 已确认信息

**⑤ 存储层**（三存储分工，禁止越界）

| 存储 | 放什么 | 绝不放什么 |
|---|---|---|
| MySQL | 条款原文、版本谱系、变更/问答/评测/反馈日志 | 向量 |
| Milvus | 双向量 + 标量过滤字段 | 条款全文（正文以 MySQL 为准，Milvus 只存 chunk 与 clause_id 引用） |
| Redis | 缓存、会话、锁、限流计数 | 任何唯一真相（全是可重建数据） |

## 2. 存储设计

### 2.1 MySQL 核心表

```
t_rule_doc      规则文档级：id, platform, doc_name, doc_type(法规/平台规则), source_url, publish_date, current_version
t_clause        条款级：id, doc_id, clause_no('2.3.1(二)'), path(章/节/条路径), title, content, scene, state_in, actor, risk_level, category, platform
t_clause_version 条款版本谱系：clause_id, version, effective_from, effective_to(NULL=现行), publish_date, content_hash, status(published/active/expired)
t_change_log    变更日志：clause_id, old_hash, new_hash, change_type(新增/修订/废止), detected_at, regression_pass, released
t_qa_log        问答日志：query, scene, risk_level, retrieved_clause_ids, answer, cited_clauses, latency_ms, cache_hit, token_cost
t_eval_case     评测集：query, gold_clause_id, gold_answer, risk_level, scene, source
t_feedback      人工反馈：qa_log_id, correct(bool), corrected_clause_id, reviewer, note
```

关键约束：**`t_clause_version` 是版本谱系的真相源**；"失效版本不删"由 `effective_to` + `status` 表达，支持申诉举证。

### 2.2 Milvus collection schema

```
clause_chunks:
  clause_id     VARCHAR   → 关联 MySQL
  chunk_no      INT16
  dense         FLOAT_VECTOR(1024)   # BGE-M3 dense
  sparse        SPARSE_FLOAT_VECTOR  # BGE-M3 sparse（词权重）
  ── 标量过滤字段（全部可先过滤）──
  status        VARCHAR   # active / published_not_effective / expired
  effective_from INT64    # unix 秒
  effective_to   INT64    # 9999-12-31 表示现行
  category      VARCHAR   # 支持通配：query 未指定时不过滤
  platform      VARCHAR
  scene         VARCHAR   # 可空
  state_in      VARCHAR   # 可空
  risk_level    VARCHAR
索引：dense-HNSW / sparse-SPARSE_INVERTED_INDEX，混合 search 用 RRF
```

### 2.3 Redis key 设计（全部带版本）

| key | 内容 | TTL |
|---|---|---|
| `rr:v{ver}:faq:{md5(归一化query)}` | FAQ 完整答案 JSON | 7d，版本变更即整体失效 |
| `rr:v{ver}:emb:{md5(text)}` | 条款/query embedding | 30d |
| `rr:sess:{session_id}` | 近 5 轮 query + 已给条款号集合 | 2h |
| `rr:lock:rebuild` | 重建分布式锁 | 自动过期 |
| `rr:rl:{api_key}:{minute}` | 限流计数 | 60s |
| `rr:meta:rule_version` | 当前规则库版本号（版本源的 Redis 镜像，MySQL 为准） | 永久 |

## 3. 两条数据流

### 3.1 查询流（主链路，13 步）

```
用户提问 → ①接入层鉴权限流 → ②NLP：意图/场景/改写/风险预判
→ ③a 命中 L3 词表 → 直接走转人工分支
→ ③b Redis FAQ 命中（版本一致）→ 流式返回（~40% 流量，<500ms）
→ ③c 未命中：Milvus 标量过滤+双向量召回 ∥ MySQL BM25 → RRF 融合 → reranker 精排 top5
→ ④风险路由定级 L1/L2 → Prompt 组装 → LLM 生成（SSE 首包尽快吐）
→ 引用校验：条款号 ∈ 召回集？否 → 重试一次 → 仍失败 → 降级仅条款原文
→ L3：只返回条款原文+风险提示+建工单（带会话上下文）
→ ⑤落 t_qa_log（含 latency/token_cost/引用），写回 FAQ 缓存
```

### 3.2 变更流（规则更新，体现"上线系统"的关键）

```
定时采集（法规源自动抓）+ 人工录入（平台规则 CSV/后台）
→ content_hash 比对 t_clause_version
→ 有变：旧版标 effective_to=新版生效日（不删）→ 新版入库（status=published_not_effective）
→ 到生效日定时任务切 active → 清 Redis 版本号 → 缓存全量失效
→ 触发回归：跑 t_eval_case 全集 → 条款引用准确率/时效正确率对比基线
→ 掉超阈值（引用准确率 -3pp 或时效 <100%）→ 阻断发布 + 告警
→ 通过 → released=true，faq:faq 重建
```

## 4. NLP 模块清单（自研部分 = 面试"增量"清单）

| 模块 | 输入→输出 | 实现方式 |
|---|---|---|
| `clause_splitter` | 规范全文 → 条款列表（章/节/条路径） | 正则 + 状态机，分隔符表含"第X条/X.X/X.X.X(一)"；**禁止跨条合并** |
| `meta_extractor` | 条款正文 → 生效期/类目/时限数字/风险等级 | 规则+词典（"自X日起施行"、金额词表、类目树） |
| `scene_classifier` | query → scene/state_in/actor | 词表匹配 + 轻量线性分类（可复用 drama_project 级联经验） |
| `query_rewriter` | 口语 query → 规则术语 query | 同义词典映射，非 LLM |
| `citation_verifier` | LLM 答案 → 合法性判定 | 条款号抽取 + 集合 membership 硬校验 |
| `risk_router` | query+场景 → L1/L2/L3 | 词表 + 场景表 `on_timeout`/`risk_level` 字段 |

## 5. 关键设计决策（面试讲述顺序）

1. **先过滤再召回**：失效/错类目条款不进候选集，而非召回后过滤——避免"top20 过滤剩 1 条"的隐性故障
2. **规则三态**：`published_not_effective` 单独成态，公示期新规可答"X 日执行"但不当现行规则答
3. **检索单元=引用单元**：按条款切、按条款引，字符切分在这个场景是范式错误
4. **缓存 key 一律带 `v{ver}`**：规则改版旧答案整体失效——短剧项目 B2 教训的直接迁移
5. **引用校验在生成之后做硬校验**：反幻觉不靠 prompt 求模型，靠 membership 检查 + 降级路径
6. **场景键（scene/state_in/actor）做检索过滤**：知识库按状态机节点组织，不按文档章节

## 6. 内存预算与本机部署（15G 物理内存约束）

| 进程 | 常驻估算 |
|---|---|
| API 进程（FastAPI + 业务逻辑） | ~300MB |
| Embedding 进程（BGE-M3 fp16） | ~2.5GB |
| Reranker 进程（bge-reranker-base，**懒加载**） | ~1.2GB（不查询时不驻留） |
| MySQL（docker） | ~800MB |
| Redis（docker） | ~100MB |
| milvus-lite（嵌入 API 进程，无独立进程） | ~500MB |
| **合计** | **~5.4GB，峰值 <8GB，安全** |

硬规则（沿用 E 节教训）：embedding 与 reranker **分进程**，各自加载后用完即释；任何同进程双模型加载顺序必须显式管理。LLM 走外部 API，不占本地显存。
