# 05 · 项目定位校验与数据来源可行性结论

> 回答三个问题：①这个项目算不算"电商系统"？②数据库数据从哪来？③知识库的专业知识从哪来、能不能自动化？
> 全部结论基于 2026-10-29 的实测，不基于推测。

---

## 一、项目定位：它是"电商领域的 AI 应用"，不是"电商交易系统"

必须把这句话说清楚，否则面试第一问就会崩。

### 电商系统分两层，本项目只做第二层

| 层 | 内容 | 本项目 | 证据/说明 |
|---|---|---|---|
| **交易系统层** | 商品、库存、下单、支付、售后单、结算 | ❌ 不做 | 这是 mall 的领域，也是你 `company_agent` 的领域；本项目的商品/订单数据只是**被查询的模拟数据** |
| **规则治理与商家服务层** | 平台规则的生产、发布、解释、判罚、申诉、商家答疑 | ✅ 做 | 真实存在于平台"规则中心 + 商家服务"与服务商（TP/客服 SaaS）产品中 |

**判断"是否符合电商"的三个标准，逐条对照：**

1. **问题域是否真实** ✅ 商家高频咨询（退货运费谁承担、扣分影响提现、活动资质）是真实生意，抖店/淘宝规则中心每天都在更新这些条款
2. **输入输出是否对齐业务流程** ✅ 输入是"带状态的商家提问"，输出是"条款号 + 原文 + 风险等级 + 是否转人工"，与客服坐席的实际动作一致
3. **指标是否可被业务验收** ✅ 条款引用准确率、时效正确率、高风险漏答率，都是平台治理/客服团队真在看的指标

### 需要坦白的风险

- 如果你投的是**电商后端/交易系统开发**，这个项目不加分（它不写订单、不写库存）。
- 如果你投的是 **AI 应用开发 / 智能客服 / 平台治理 / 服务商产品**，它非常对口——服务商（乐言、晓多这类）的产品形态和它几乎一样。
- 项目集分工：`company_agent`（写操作、权限、事务）补交易与执行侧，`rules_rag` 补知识与合规侧。**两个加起来才覆盖"电商"这个词**，单看任何一个都不完整。

## 二、数据库数据从哪来

**不存在一份现成的"电商规则数据库"可以下载。** 这个项目的数据是自己产出的，分四类，来源完全不同：

| # | 数据 | 表 | 来源 | 谁做 | 量级 |
|---|---|---|---|---|---|
| 1 | **规则条款**（知识库本体） | `t_rule_doc` / `t_clause` / `t_clause_version` | 官方公布文本 → 解析入库 | 你提供原文 + 我做解析 | 法规 5–8 部（约 400–600 条）+ 平台规则 80–150 条 |
| 2 | **业务模拟数据** | `t_shop` / `t_merchant` / `t_order` / `t_aftersale` | **合成**（脚本生成） | 我写生成器 | 商家 50 / 店铺 50 / 订单 5,000 / 售后单 800 |
| 3 | **问答日志** | `t_qa_log` | 运行时产生 | 自动 | 随使用增长 |
| 4 | **评测集** | `t_eval_case` | 由条款反向生成问题 + 人工确认 | 我生成候选 + 你确认 | 300 条（分层） |

**关于第 2 类必须诚实**：业务模拟数据是**合成的**，只能用于演示"带状态的提问"链路（如"这个订单已发货，买家申请仅退款"），不能声称是真实商家数据。简历/面试里写"模拟业务数据"不丢人，写"真实商家订单"被追问就是硬伤。

**关于第 4 类的方法**：从条款反向造问题，是唯一能保证"标准答案有出处"的做法——先有 `gold_clause_id`，再写问题。反过来（先想问题再找条款）必然出现"找不到对应条款"的废题。

## 三、知识库的专业知识从哪来（实测结论）

### 3.1 数据源实测（2026-10-29 复测）

| 源 | 状态 | 正文可取 | 结论 |
|---|---|---|---|
| `samr.gov.cn` 市场监管总局 | 200 / 16KB 真 HTML | 首页可读，**栏目页 JS 渲染** | 可作为入口，规章正文需逐篇定位 |
| `flk.npc.gov.cn` 国家法律法规库 | GET 返回 SPA 壳（552B），POST 405 | ❌ 接口需逆向，bundle 内无明文 API 路径 | **不做爬虫依赖** |
| `www.gov.cn` 中国政府网 | 本机访问 000 / 301 | ❌ 不可达 | 需你手动下载后放入 `data/raw/` |
| `school.jinritemai.com` 抖音规则 | 200 / 4.7KB 壳；接口 502；页面带 argus 风控脚本 | ❌ | 自动化成本极高且不稳定 |
| `rulechannel.taobao.com` 淘宝规则 | 200 / 1KB 壳 | ❌ | 同上 |
| `rule.jd.com` 京东规则 | 200 / 3KB 壳 | ❌ | 同上 |

**结论一句话：四大平台规则中心全部 JS 渲染 + 风控，法规库接口需逆向且不稳定。因此"自动抓取海量条款"这条路不通，必须走"人工提供原文 + 自动解析入库"。**

### 3.2 三层知识来源，量与成本

| 层 | 内容 | 获取方式 | 我的能力边界 |
|---|---|---|---|
| **L1 法规层**（5–8 部，约 500 条） | 电子商务法、网络交易监督管理办法、消费者权益保护法、广告法（极限词）、价格法、反不正当竞争法、GB/T 47746—2026 | 你从官方页面/PDF 下载放进 `data/raw/`，我写解析器自动切条款 + 提取施行日期 | ✅ 我能搞定解析与入库（除原文获取） |
| **L2 平台规则层**（80–150 条） | 抖店/淘宝《商家售后服务管理规范》《违规行为管理规则》《结算规则》等关键条款 | **你逐条复制录入**（我提供 CSV 模板 + 候选条款清单 + 校验脚本） | ⚠️ 我只能提供模板与校验，**原文必须你取** |
| **L3 类目细则层**（20–40 条） | 生鲜/3C/服饰的退货与资质差异 | 同上 | ⚠️ 同上 |

### 3.3 为什么 L2 必须你亲手做（这不是甩锅）

1. **技术原因**：原文在 JS 渲染 + 风控后面，我没有登录态，拿不到。
2. **可信度原因**：面试官问"这条 36 小时你从哪看的"，答"《商家售后服务管理规范》2.3.1(二)"和答"AI 给我的"是两档。**"我读过规则"本身就是这个项目的可信度来源。**
3. **不可编造原则**：条款号一旦编错，整个引用溯源体系的价值归零。所以我的纪律是：**无 `source_url` + 原文快照的条目不进库**。

### 3.4 我能替你做到的"减负"部分（把写文章变成填空）

- ① 目录与命名规范（`data/raw/{platform}/{doc_name}_{publish_date}.html|pdf`）
- ② 解析器：HTML/PDF → 条款树（章/节/条），自动提取"第X条"、施行日期、"自X日起施行"
- ③ 录入模板：CSV 七列（doc_name, clause_no, content, effective_from, category, scene, source_url），Excel 直接填
- ④ **候选条款清单**：我按"12 个高频场景"列出"应该去哪个文档的哪一节找"，你只需定位复制
- ⑤ 校验脚本：检查条款号连续性、日期合法性、空字段、重复、缺 source_url → 不合格不入库
- ⑥ 评测集候选：从已入库条款自动生成 300 条问题草稿，你只需判断"这题商家真会问吗"

## 四、降风险路线（如果 L2 录入太慢）

**Plan B：先 L1 + 国标跑通，平台规则后补。**
- L1 法规 500 条足以支撑 100–150 条评测集，能证明"条款级检索 + 时效过滤 + 引用校验"三条技术主线
- 平台规则作为 P2 增量插入（架构不变，只是多一批 source）
- 简历表述相应改为"覆盖法规与平台规则双源"，不夸大成"全平台规则库"

**这比"凑一堆爬来的脏数据"更安全**：全量但无法标注 = 没有评测集 = 无法证明准确率。

## 五、结论汇总表

| 问题 | 结论 |
|---|---|
| 项目符合电商吗 | 符合**规则治理/商家服务**域，不属于交易系统域；投 AI 应用/客服/治理岗对口，投交易后端不对口 |
| 数据库数据哪来 | 条款靠"人工原文 + 自动解析"；业务表靠**合成**；日志运行时产生；评测集由条款反向生成 |
| 专业知识能搞定吗 | **法规层我能搞定 90%（除原文下载）**；平台规则层我能搞定 70%（模板+校验+候选清单），**原文必须你取** |
| 最大风险 | 不是技术，是 L2 原文获取的人工成本；用 Plan B 可控 |
