## 验证一：改一条条款 → 旧版标 expired（不删）+ 新版 version=2

> 为什么旧版正文放 `t_clause_history» 而不是在 `t_clause» 里留两行：
> `t_clause» 上有 `UNIQUE INDEX (doc_id, clause_no)»，同一 (文档, 条款号) 物理上只允许一行。
> 要硬留两行必须先拆掉唯一索引，而唯一索引正是"同一条款被重复入库"的最后一道防线。
> 所以：`t_clause» 永远只放现行内容，历史单独成表。

## 验证二：改前问一次命中缓存、改后同问返回新内容

**为什么要专门写个脚本**：缓存的 key 公式必须和 `/api/chat» 完全一致，手敲的 key 验的是手稿。
另外本机没有 Redis，进程内存缓存不跨进程共享 —— 分两次命令行跑，第二次必然是 miss，
那样就分不清"是版本号把它隔离了"还是"进程重开了"。所以前后两段放在同一进程里跑。

**真实输出（全文）**：

```
阶段一：变更前，同一个问题问两次
  [1st] 规则版本=v5  未命中(现算并写入)
         key=rr:v5:chat:66f6181b:620c45589c083334149002093c957106
         引用=《商家售后服务管理规范》2.2  时限=['24 小时']
  [2nd] 规则版本=v5  命中缓存
         key=rr:v5:chat:66f6181b:620c45589c083334149002093c957106
  -> 第二次 命中，证明缓存链路本身是通的

阶段二：改原文 -> 跑流水线
  [diff] 修改 1 / 新增 0 / 下线 0
  [4/6 bump] 规则版本 v5 -> v6
  [发布] 门禁通过

阶段三：变更后，同一个问题再问两次
  [3rd] 规则版本=v6  未命中(现算并写入)
         key=rr:v6:chat:66f6181b:620c45589c083334149002093c957106
         引用=《商家售后服务管理规范》2.3.1  时限=['36 小时']
  [4th] 规则版本=v6  命中缓存
         key=rr:v6:chat:66f6181b:620c45589c083334149002093c957106
  -> 第三次 未命中：key 前缀（规则版本）变了，旧缓存整体隔离
  -> 第四次 命中：新版本下缓存重新生效

```

**结论**：同一个问题，改前 `rr:v5:…» 命中缓存，改后 key 变成 `rr:v6:…»，
旧条目再也取不到，答复内容随条款变化。这证明"规则版本进缓存 key"这条链是通的。

**同时暴露一个真实问题（如实记录）**：给 2.2 加了一句括注后，
Top1 从 `2.2» 漂到了 `2.3.1»（36 小时）。单通道 BM25 下 Top1 对措辞高度敏感，一格之差就换条款。
这既说明精排/向量通道的价值，也说明为什么必须有 P10 那套回归门禁盯着 Top1。

## 门禁为什么是两条时效红线

| 红线 | 分母 | 语义 | 容差 |
|---|---|---|---|
| 时效正确率(端到端) | **全部**时效题 | 用户到底有没有拿到时限 | ≥ baseline − 3pp |
| 时效一致性 | 引用了**正确条款**的时效题 | 说依据这条，就必须说出这条的时限 | **必须 100%** |

只留端到端，"引用对了但没说出时限"这类错会被绝对数值淹没；
只留一致性，召回一变差，题就从分母里掉出去，指标反而显示 100% —— 那正是"把指标调成凑数"。
这次是**真的踩到了**：最初只做了 scoped 版本，结果第一次注入坏改动时门禁放行了（时效仍显示 100%），
因为受影响的题恰好都掉出了分母。两条一起卡之后才拦住。这个教训写在这里。

## 已知限制（如实记录，不粉饰）

1. **向量重建被跳过**。本机没有 `FlagEmbedding» / BGE 模型，编码器起不来，
   `rebuild» 阶段如实写 `skipped: encoder_unavailable» 并记进 `t_change_log»，
   **没有假称"已重建"**。检索此时完全依赖 BM25 —— 这也是验证二里 Top1 漂移更明显的原因。
   装了 BGE 之后这一步会真正增量重编码（`VectorIndex.build(force=True)»）。
2. **本机无 Redis**，规则版本号落在 `data/rule_version.json»。有 Redis 时同一套 API
   会把号写进 `rr:rule_version» 键，行为一致。
3. **流水线只处理已在库的文档**。新增文档仍走 `pipeline/build_store.py»；
   变更流水线管的是"已入库规则怎么安全更新"，不是"怎么新增规则库"。
