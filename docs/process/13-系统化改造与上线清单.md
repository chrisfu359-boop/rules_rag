# 13 · 从单页 Demo 到可上线系统

> 改造前的状态：一个 `demo/index.html` + 无用户体系 + 任何人都能调接口。
> 改造后：多页面应用、三种角色、会话历史、数据隔离、审计日志、可在后台改模型配置。

## 一、分层结构

```
web/                      前端（原生 HTML/CSS/JS，无构建步骤）
├── login.html            登录 / 注册
├── app.html              工作台（会话 + 对话 + 条款引用 + 反馈）
├── rules.html            规则库检索浏览
├── settings.html         个人资料 / 偏好 / 店铺 / 改密码
├── admin.html            用户管理 / 模型配置 / 审计日志
├── legacy.html           早期单页 Demo（保留对比）
└── assets/
    ├── style.css         设计系统（变量驱动，深浅色）
    └── api.js            请求封装 / 登录守卫 / Toast / 主题

api/                      接口层（FastAPI Router）
├── security.py           JWT、bcrypt 校验、角色守卫、登录限流
├── schema.py             7 张表 DDL（MySQL + SQLite 两套）+ 种子账号
├── auth.py               注册 / 登录 / 登出 / me / 改密码
├── chat.py               会话 CRUD / 问答 / 反馈 / 个人看板
├── settings.py           资料 / 偏好 / 店铺
├── rules.py              规则库检索与浏览
└── admin.py              用户管理 / 模型配置 / 审计 / 全站指标

service/                  业务层
├── qa.py                 Runtime + answer()：检索→路由→生成→校验
└── cache.py              Redis/内存缓存 + 限流
```

**为什么把问答逻辑从视图里抽出来**：接上用户系统后问答有两个入口（新的 `/api/chat/ask`
和保留的 `/api/ask`）。逻辑留在视图函数里，两份必然分叉——改了一处忘了另一处，
是这类项目最常见的退化。

## 二、数据模型

| 表 | 作用 | 关键点 |
|---|---|---|
| `t_shop` | 店铺 | 商家账号关联一个店铺 |
| `t_user` | 用户 | `role` 三种：merchant / ops / admin；`status` 控制启停 |
| `t_chat_session` | 会话 | 每会话属于一个用户，`message_count` 冗余计数避免列表页 count |
| `t_chat_message` | 消息 | `role` 只有 user/assistant；`citations` 存 JSON 条款快照 |
| `t_feedback` | 反馈 | `UNIQUE(message_id, user_id)`，一人一票，改主意即覆盖 |
| `t_user_pref` | 偏好 | 主题 / 默认场景 / 回答风格 |
| `t_audit_log` | 审计 | 登录、失败、注册、改配置、改权限全留痕 |

**为什么 `citations` 存快照而不是外键引用条款**：条款会被修订、会失效。
如果只存 clause_id，三个月后回看历史会话，看到的是"现在的条款"而不是"当时的条款"——
合规场景里这是致命的，审计要还原的是当时依据了什么。

## 三、权限模型

```
未登录  → 页面 302 跳 /login；接口 401
merchant → 只能看自己的会话；角色为 merchant
ops     → 平台运营，可查看规则库，无管理权
admin   → 管理后台全部功能
```

三条硬规则：

1. **每条会话查询都带 `user_id` 条件**，不是"先查出来再判断 owner"。
   后者只要有一处忘了判断就是越权，而且很难发现。
2. **角色每次从数据库读，不信 JWT 里的 role**。token 有效期 7 天，
   如果这期间把某人从 admin 降级，读 token 的写法会让他继续当 7 天管理员。
3. **前端隐藏按钮不算权限**。`/admin` 页面服务端直接判角色，接口再加一层 `require("admin")`。

实测验证（`merchant` 账号）：

| 操作 | 结果 |
|---|---|
| 看自己的会话列表 | 0 条（正确，是真的没有） |
| 直接访问别人的会话 ID | **404**（不是 403——不暴露"该会话存在"这个信息） |
| 调 `/api/admin/metrics` | **403** |
| 访问 `/admin` 页面 | **302 → /app?denied=admin** |

## 四、安全设计

| 项 | 做法 | 为什么 |
|---|---|---|
| 密码存储 | bcrypt cost=12 | sha256 太快，GPU 每秒十亿次；bcrypt 故意慢且自带 salt |
| 会话凭证 | JWT → **httpOnly cookie** | localStorage 的 token 任何 XSS 都能读走 |
| JWT 密钥 | 首次启动生成随机密钥写 `.jwt_secret`（600） | 硬编码进 git 等于公开，谁都能伪造 token |
| 登录防爆破 | 5 分钟内 5 次失败锁定，按 `用户名+IP` | 只按 IP 会误伤 NAT 后的整个办公室 |
| 错误提示 | 统一"用户名或密码错误" | 区分"用户不存在"会变成账号枚举接口 |
| 输出编码 | 前端所有动态文本过 `esc()` | 用户问题会原样回显，不转义就是现成的 XSS |
| 停用账号 | 登录时校验 + 每次请求校验 | 只拦登录的话，已登录的人还能用 7 天 |
| 自锁防护 | 管理员不能改自己的角色/状态 | 否则最后一个管理员一点就锁死全系统 |

## 五、这一轮踩的四个真坑

### 1. 时区：容器 MySQL 是 UTC

`created_at` 显示比本地时间少 8 小时。因为 Docker 里的 MySQL 默认 `UTC`，
而 `DEFAULT CURRENT_TIMESTAMP` 写入的是数据库时区的时间。
**修法**：连接时 `init_command="SET time_zone='+08:00'`，同时所有 INSERT 显式传 Python 生成的本地时间。
只修一处不够——漏掉的那处会在某天悄悄写错。

### 2. BGE-M3 懒加载，首问 9~12 秒

向量库启动时只加载了矩阵，编码器是这个模型最重的部分，第一次 `encode` 才加载。
结果是**第一个提问的用户替所有人承担了加载开销**。
**修法**：启动时用一句话预热 `vindex.encode(["预热"])`。首问从 9.3 秒降到 4.8 秒。

### 3. 缓存命中却显示旧的耗时

答案整条缓存，包括 `latency_ms`。命中缓存时直接返回，界面显示"4854ms"——
用户完全看不出缓存起作用了。
**修法**：命中时用本次真实耗时覆盖该字段，现在是 4~8ms。

### 4. 返回体字段不一致

`/api/chat/ask` 返回 `clauses`，会话详情返回 `citations`，前端只认 `citations`。
表现是"对话里刚问完能看见条款，刷新页面就没了"。
**修法**：两处都返回，字段名统一。这类 bug 不会报错，只会让功能悄悄失灵。

## 七、上线前还差的（诚实清单）

1. **HTTPS**。cookie 现在 `secure=False`，上线必须设 `COOKIE_SECURE=1` 并配证书。
2. **CSRF token**。现在靠 `SameSite=Lax` 兜底，对跨站 POST 有效，但表单型攻击的边界要再收。
3. **多实例部署**。JWT 无状态没问题，但登录失败计数和缓存用的是进程内存（Redis 可用时走 Redis），
   多实例需要强制 Redis。
4. **数据库迁移**。现在靠 `CREATE TABLE IF NOT EXISTS`，改字段要手工 ALTER。
   字段一旦频繁变更就该上 Alembic。
5. **备份**。会话和审计日志没有备份策略。
6. **前端无构建**。原生 JS 到这个体量还行，页面再多应该上框架。
7. **大模型配置写 .env**。多实例部署时应该改为配置中心或数据库 + 热加载。

## 八、面试怎么讲（90 秒版）

> 我最初做的是个单页 demo，后来按可上线的标准重做了一遍。
> 主要补了四块：用户体系、数据隔离、审计、以及把问答逻辑从视图里抽出来做成服务层。
>
> 用户体系用 JWT 但放 httpOnly cookie，不放 localStorage；角色每次从库里读，
> 因为 token 有 7 天有效期，改权限必须立即生效。
> 数据隔离我没用"查出来再判断 owner"，而是在每条 SQL 里带 user_id，
> 因为前者只要漏一处就是越权。实测商家账号访问别人的会话返回 404 而不是 403——
> 不暴露"这个会话存在"。
>
> 这轮踩了四个坑都挺典型：容器里 MySQL 是 UTC 导致所有时间差 8 小时；
> BGE-M3 懒加载让第一个提问的用户等 9 秒，我在启动时预热掉了；
> 缓存命中却显示旧的耗时，优化在界面上完全看不出来；
> 还有两个接口返回的字段名不一致，前端刷新后条款就消失了。
> 这四个都不是报错型 bug，是那种"功能在悄悄不对"的。
