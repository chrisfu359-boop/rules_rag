## 一、先说一个必须记录的故障

**Docker Desktop daemon 中途退出，MySQL / Redis / Milvus 全部不可用，且无法恢复。**

- `wsl.exe` 被本机安全策略列入程序黑名单（Security Center → Command Security），Docker Desktop 依赖 WSL2 后端，因此起不来
- 这不是代码问题，也无法通过改代码绕过

**处理方式：存储层改为双后端，默认 SQLite。**

这不是临时打补丁，而是有意的架构选择：

| 项 | 说明 |
|---|---|
| 表结构 | `pipeline/build_sqlite.py` 与 MySQL 版逐字段一致（8 张表的字段名/类型/索引全部对应） |
| 切换方式 | `common.backend()`：默认 `sqlite`，要 MySQL 必须显式 `DB_BACKEND=mysql` |
| 上层代码 | `pipeline/`、`retrieval/`、`app.py` 的调用接口完全不变 |

**为什么改成"默认 SQLite"而不是"探测 MySQL"**：中途 MySQL 恢复过一次，里面还是旧的 353 条（不含平台规则），而 SQLite 里是 406 条。两个后端数据不一致时"谁活着用谁"，会让平台规则凭空消失，而日志看上去一切正常。**这与"缓存不带规则版本号"是同一类故障：状态有两个来源，就必须确立唯一权威。** 这一条本身就是可讲的工程判断。

### 关于平台规则数据的诚实说明（重要）

规则中心是前端渲染页面 + 风控，`curl` 与 `WebFetch` 均取不到正文（已留多轮实测证据）。因此两份平台规则文件：

- **架构、售后类型划分、时限数值**（24h / 36h / 48h / 7天 / 扣分节点 2-12-24-48 分 / 账期延长 15-30-60 天）来自公开资料与规则中心页面摘要，多方交叉比对一致
- **表述文字是整理稿，不是官方逐字原文**，front-matter 已标 `verified: false`
- **面试时不能说"这是官方原文"**。正确说法是："平台规则我按公开资料整理成结构化条款，标注了未核验标记，正式使用需对照规则中心复核。"——**这个标注本身就是加分项，比假装是原文安全得多。**

## 三、检索：BM25 + BGE-M3 双通道 RRF 融合

| 项 | 实现 |
|---|---|
| 词法通道 | 自研 BM25（jieba 分词 + 同义词扩展 + 扩充虚词停用表） |
| 语义通道 | BGE-M3 dense（1024 维，本地模型，未下载任何新依赖） |
| 融合 | RRF（k=60，等权），**不做分数加权**——BM25 分数无上界、余弦在 0~1，量纲不同，归一化后加权会引入"按候选集大小漂移"的问题，正是 EduRAG 里 BM25 softmax 阈值那个 bug 的同源问题 |
| 向量存储 | 本地 `vectors.npz`（406×1024）。Milvus 19530 端口在，但 pymilvus 连接返回 `illegal connection params or server unavailable`；406 条规模暴力内积 < 1ms，不需要独立向量库进程 |
| 接口 | `search(query, top_k, scene)` 与 BM25 完全一致，后续换 Milvus 只改两个方法 |

### 三个真实 bug（都可作为面试素材）

1. **平台规则只切出 13 条**：`level=3` 时"2.1 目的"被当成小节标题吞掉 → 改混合层级，父条只有标题时丢弃，从 13 → 29 条
2. **`low_conf` 阈值失效**：从 BM25 换成 RRF 后，分数从几十变成 0.03 量级，原阈值 8.0 会让**所有问题**都被判成"低置信"→ 改为 0.02。**换检索器时必须同步检查所有依赖分数绝对值的判断。**
3. **后端选错导致数据凭空消失**：见第一节
