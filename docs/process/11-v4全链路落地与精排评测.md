## 二、评测结果（同一套 18 题，同一个评测脚本）

| 链路 | Top1 | Top3 | P50 | P95 |
|---|---|---|---|---|
| BM25 + 向量(向量走 npz)，无精排 | 10/18 = 55.6% | 14/18 = 77.8% | 351ms | 436ms |
| 纯精排（alpha=0），候选池 8 | 10/18 = 55.6% | 15/18 = 83.3% | — | — |
| **精排 + RRF 融合权重 0.05（当前线上）** | **11/18 = 61.1%** | **15/18 = 83.3%** | **2255ms** | **2883ms** |

三条结论：

1. **精排不是银弹**。纯精排的 Top1 和纯 RRF 一样是 55.6%，只把 Top3 拉到 83.3%。
   原因在第四节：精排分挤在 0.95~0.998，排序实际由小数第三位决定。
2. **加一个很小的 RRF 先验才有增益**（alpha=0.05 → 61.1%）。这个权重是
   `pipeline/exp_blend.py` 扫出来的，不是拍脑袋。
3. **延迟换准确率的账要算清楚**：P50 从 351ms 涨到 2255ms（6.4×）。
   所以必须配 Redis 缓存（命中 2~5ms）和 `RERANK=off` 开关，否则演示会卡。

### 还错的 3 题（如实列出）

| 问题 | 期望 | 实际 | 性质 |
|---|---|---|---|
| 七天无理由退货的七天从哪天开始算？ | 七日办法 第八条 | 第十条 | 真错，两条款都在讲"七日"的计算 |
| 售后超时未处理会怎样？ | 售后规范 3.1 | 2.4.4 | 真错，超时后果 vs 超时处理时限，语义近 |
| 直播带货的广告谁负责？ | 互联网广告办法 第十四条 | 第十九条 | **标注偏严**：第十九条同为直播带货责任条款，可接受 |

前两条是真实缺陷，第三条是评测标注口径问题——**不为了让指标好看去改 gold**，
只在文档里标注清楚。另外"网上开店需要办营业执照吗"命中《网络交易监督管理办法》第十二条
而非《电子商务法》第十条，属于同义条款，按严格口径记 MISS。

## 三、四个真实故障（面试可直接讲）

### 1. 向量与主键错位：406 条只灌进 315 条

现象：`build_milvus.py` 打印 `count: 315`，但语料明明是 406 条，且没有任何报错。

原因：`npz` 里的 `id` 是 1..406 的**顺序号**（按 `load_clauses()` 的返回位置生成），
而 MySQL 里 `t_clause.id` 有断层——旧库 353 条删改过，自增序列跳到 1074。
用 id 去 join 元数据时，只对上了 315 条。

修法：**向量必须在与元数据同一次快照下生成**。重跑 `vector_store.py --force`，
按当前库的 406 条重新编码，再灌 Milvus，条数一致。

教训：`zip` 两个长度不同但"看起来都很大"的集合时，错误是静默的。
要校验的不是"条数对不对"，而是"id 集合是否完全相同"。

### 2. `sentencepiece` 打不开中文路径

现象：加载 `bge-reranker-large` 报
`Unable to load vocabulary from file. Please check that the provided vocabulary is accessible`。
文件明明在（`ls` 能看到 5MB 的 `sentencepiece.bpe.model`）。

原因：模型原始路径含中文（`zzl_ai_面试`）。`sentencepiece` 是 C++ 库，
Windows 下走窄字符 API，无法打开非 ASCII 路径。`xxd` 能读、Python 能读，只有它读不了。

修法：建 ASCII junction 指过去（不复制 2.2G、不下载、不动原目录）：

```powershell
New-Item -ItemType Junction -Path "G:\models\bge-reranker-large" `
         -Target "G:\hm_st\sf_zj\project\zzl_ai_面试\bge-reranker-large"
```

顺带解释了一个"为什么 BGE-M3 没事"：它的 tokenizer 走 `tokenizer.json`（纯 JSON），
不进 C++ 的 sentencepiece 加载路径。

### 3. 开了精排，Top1 涨了但 Top3 一动不动

现象：精排上线后 Top1 55.6→61.1%，Top3 稳定在 77.8%，一点没变。

原因：`hybrid.search` 先把融合结果截成 `top_k`（评测传 3），再送给精排。
精排只能在 3 条里重排，Top3 集合天然不会变。等于花了 2 秒做无用功。

修法：给精排留够候选——`want = max(top_k, rerank_pool)`，先取 4~8 条再精排回 top_k。
改完 Top3 立刻变成 83.3%。

教训：**"加了精排没效果"先看候选集是不是被上游截断了**，别急着换模型。

### 4. 低置信阈值又失效了（第二次踩同一个坑）

精排分是 0~1 的归一化概率，RRF 分是 0.03 量级。原来写死的阈值 0.02 在精排通道下
等于"永不低置信"，垃圾问题也会硬答。

修法：阈值跟着通道口径走 —— `thr = 0.30 if 精排可用 else 0.02`。
和 v3 那次"换 RRF 后阈值 8.0 失效"是同一类错误：**任何依赖分数绝对值的判断，
换检索器/排序器时必须重新标定**。这次把阈值写进了 `/api/ask` 的 trace 里，
方便线上回看当时用的是哪套口径。

## 四、精排为什么必须和 RRF 分融合

`bge-reranker-large` 对"都相关"的条款给出 0.95~0.998 的分数，彼此差距在千分位。
前 4 条候选里三条都 >0.99 时，排序实际由噪声决定。

实测（`pipeline/exp_blend.py`，18 题，候选池 8）：

| 策略 | Top1 | Top3 |
|---|---|---|
| 纯 RRF | 55.6% | 77.8% |
| 纯精排 alpha=0 | 55.6% | 83.3% |
| 精排 + 0.05 × 归一化 RRF | **61.1%** | **83.3%** |
| 精排 + 0.2 × 归一化 RRF | 55.6% | 83.3% |

alpha 太小没用、太大退化成 RRF，0.05~0.1 是拐点。这是"两个排序器都不可信时，
用对方的弱先验做 tie-break"的典型用法。

### 参数是怎么定的

`pipeline/bench_rerank.py` 扫了 5 组（pool × max_length × 正文截断）：

| 配置 | 平均耗时 | Top1(3 题抽样) |
|---|---|---|
| pool10 / ml256 / 300 字 | 6.21s | 3/3 |
| pool8 / ml192 / 200 字 | 3.82s | 3/3 |
| pool6 / ml192 / 200 字 | 2.60s | 3/3 |
| pool6 / ml160 / 160 字 | 2.52s | 3/3 |
| pool5 / ml128 / 120 字 | 1.79s | 3/3 |

最终取 **pool4 / ml160 / 150 字**，全量 18 题复核 Top1/Top3 不掉（61.1%/83.3%），
P50 从 3284ms 降到 2255ms。**先定准的边界，再往里压参数**。

## 五、现在这套系统的能力边界

**能做的**

- 406 条条款按现行有效过滤后检索，回答附条款号 + 原文 + 生效日期 + 官方链接
- L1/L2/L3 三档风险路由，L3（罚款/定性）强制转人工且不给结论
- 引用校验：结论里出现的条款号必须来自召回集，防编造
- 四组件探活 `/api/health`、指标在线 `/api/eval`、问答审计落 `t_qa_log`
- 组件级降级：MySQL 挂了走 SQLite、Milvus 挂了走 npz、精排挂了走原序、Redis 挂了走内存

**还不能做的**

- 答案是**模板抽取**，不是 LLM 生成（语言生硬，但引用 100% 可核对）
- 评测集只有 18 题，没有回归门禁（改一次参数只能手动跑一遍）
- 精排 1.9s/次，CPU 极限；没有 GPU、没有 ONNX 加速、没有批量推理
- 平台规则两份是整理稿 `verified=false`，需对照平台规则中心逐字复核
- 没有多轮对话、没有工单系统对接、没有权限分级（商家/平台/审核员）
