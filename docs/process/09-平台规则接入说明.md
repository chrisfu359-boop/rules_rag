## 2. 三步完成接入

### 第 1 步：复制正文

打开规则页面，`Ctrl+A` → `Ctrl+C`，粘进一个 utf-8 文本文件（如 `粘贴.txt`）。

**只要正文，不用整理格式**。编号 `2.3.1` 原样保留即可，解析器认这个。

### 第 2 步：一条命令入库

```bash
cd G:/hm_st/sf_zj/code/coze_dify/homework/project/rules_rag

python pipeline/ingest.py \
  --name "商家售后服务管理规范" \
  --platform douyin \
  --effective-from 2026-09-15 \
  --source-url "https://school.jinritemai.com/doudian/web/article/104600" \
  --file 粘贴.txt
```

- `--source-url` **必填**。没有出处的条款不入库——编条款号比没有条款更糟。
- `--mode` 一般留空，自动识别法条（第X条）/ 平台三级编号（2.3.1）/ 平台二级编号（x.y）。
- 生效日期不确定就留空，但**必须填 source_url**，否则日后无法核对版本。

### 第 3 步：切分 + 入库 + 重启

```bash
python pipeline/clause_splitter.py && python pipeline/build_store.py
# 然后重启 app.py
```

## 3. 需要哪几个页面（按优先级）

| 优先级 | 页面 | 覆盖场景 | 价值 |
|---|---|---|---|
| **P0** | 商家售后服务管理规范（现行版） | 仅退款/退货退款/换货/补寄/维修的**商家处理时限**与**超时后果** | 解决"我多久要处理"这类最高频问题，且**法规层完全没有** |
| **P0** | 七天无理由退货服务规范 | 平台层面对七天的细化（适用范围、商品完好判定） | 与法规第十八条形成"法规+平台"双层引用 |
| **P1** | 商家违规行为管理规则（含违规处理/扣分） | 扣分、处罚、申诉 | 对应 L3 高风险场景，也是"处罚代价"的来源 |
| **P1** | 保证金管理规则 | 保证金扣除、赔付划扣 | 与上面的"违约金 30%（最低 6 元，最高 50 元）"呼应 |
| **P2** | 结算/账期规则 | 账期延长、冻结 | 打通"治理→资金"这条链（淘宝 2/24/48 分 → 15/30/60 天） |

**最小可用集：前两个 P0。** 只补这两个，第 4 个演示场景（仅退款时限）就能答对。

## 4. 入库后的验收标准（我会当着你面跑）

1. **条数与页面编号对得上**：页面最后一条是什么，切出来最后一条就该是什么
2. **跨条违规 = 0**：任一条正文里不应出现下一条的编号
3. **编号原样保留**：`2.3.1` 不能变成 `2.3.1.` 或 `2`
4. **能答对第 4 个场景**：问"仅退款多久处理"→ 命中 `2.3.1`，且引用校验通过

不达标就不算接完，我不会说"已完成"。

## 5. 顺带发现的一个真实案例（面试可用）

抖音《商家售后服务管理规范》同时挂着两个版本：

- 现行版（20251203 之后的 20260914 版）
- **标注「已失效（20251203 版本于 20260914 失效）」的历史版**

而两版的换货处理时限**不一样（36 小时 / 48 小时）**。

这不是我编的场景，是平台自己挂在页面上的。它直接证明了三件事：

1. **"知识过期比没有知识更危险"**——搜到旧版就答错，而且答得很自信
2. **失效版本不能删**——商家申诉时要引用"当时适用"的条款
3. **缓存 key 必须带版本号**——否则规则更新后用户持续拿到旧答案，而缓存命中率看起来一切正常

这三条在我的设计文档里都写了，现在有了**平台官方页面做证据**，不是我推测的。
