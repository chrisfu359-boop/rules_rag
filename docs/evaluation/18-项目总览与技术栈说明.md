## 一、这个项目是什么

**电商规则合规助手**：面向商家、买家、平台运营三类业务角色 + 一个系统管理员的规则问答与治理系统。

它不是一个"接了大模型的客服机器人"。核心承诺只有一句：

> **每句结论都必须落到一条现行有效的条款上；落不到就说没有依据；涉及处罚金额与法律定性，不由 AI 给结论。**

这条承诺落到工程上是三个闸门：

1. **存储层先过滤**：只检索 `status='active'» 的条款版本，过期规则天然不可见。
2. **生成层引用校验**：把结论里出现的条款号与召回集逐一比对；模型编造编号 → 带上下文重试一次 →
   仍编造则整条退回模板答案（不是删掉引用，删引用会让结论变成没有出处的断言）。
3. **路由层风险分级**：纯规则判 L1/L2/L3（单次 < 5ms，因为这层每次请求都要跑），
   L3 强制转人工并落真实工单。

在此之上叠了两层真实业务：**智能客服**（四级漏斗 Redis → FAQ BM25 → 大模型 → 人工）
与**平台监管**（买家投诉 → AI 调解决定 → 自动/人工裁决 → 扣分累计 → 节点处罚 → 申诉回滚）。

## 二、技术栈

| 层 | 选型 | 为什么选它（而不是更常见的那个） |
|---|---|---|
| Web 框架 | FastAPI 0.115 + Uvicorn | 异步 + Pydantic 校验；接口 schema 就是文档 |
| 数据校验 | Pydantic v2 | 入参出参同一套模型，避免"接口收什么、返回什么"两处维护 |
| 主存储 | **SQLite / MySQL 双后端**（同一套表结构） | 这个规模（406 条款 + 5005 订单）不需要独立 DB 进程；把存储做成可替换，比绑死 MySQL 更工程化。默认 SQLite，要 MySQL 必须显式设 `DB_BACKEND=mysql» |
| 缓存 | Redis（可降级为进程内存） | 缓存 key **带规则库版本号**，规则一变全量隔离；限流不因 Redis 挂掉而失效 |
| 词法检索 | 自研 BM25（jieba 分词 + 同义词 + 稀有词加权 + 场景软过滤） | 条款号、专有名词这类精确串，词法比语义可靠 |
| 语义检索 | BGE-M3 dense（1024 维）+ **Milvus IVF_FLAT/IP**，npz 本地兜底 | 双通道；两路都用 RRF 融合，避免量纲问题 |
| 融合 | **RRF（k=60，只看名次）** | BM25 分数无上界、余弦在 0~1，归一化再加权会按候选集大小漂移 |
| 精排 | bge-reranker-large cross-encoder（候选池 4，与 RRF 分加 0.05 先验融合） | 召回宽、精排窄；0.05 这个权重是 `pipeline/exp_blend.py» 实验定的，不是拍的 |
| 生成 | 任意 **OpenAI 兼容协议**（DeepSeek / 通义 / Kimi / GLM / OpenAI / Ollama / vLLM） | 换厂商是改 `base_url»，不是改代码；未配置时自动退回模板，服务不报错 |
| 路由 / 查询理解 | 纯规则（7 类场景词表 + 17 个风险词 + 时限正则） | 每次请求都跑，LLM 单次 300~800ms，高频场景不划算；规则可解释、可审计 |
| 鉴权 | JWT（httpOnly cookie）+ bcrypt + 登录防爆破 | 四角色 RBAC；越权返回 404 而不是 403，不暴露数据是否存在 |
| 前端 | **原生 HTML + CSS + JS，无框架、无构建** | 11 个页面 + 1 个独立演示页；没有构建链就没有构建链的故障 |
| 测试 | 4 套 e2e（真实 uvicorn + 真实 HTTP） | 211 项断言，覆盖四角色权限与裁决链路 |
| 评测 | 自建 300 条分层评测集 + 四项门禁 | 把"改规则会不会改坏效果"变成 exit code |
| 部署 | Dockerfile + docker compose（app / MySQL / Redis / Milvus / etcd / minio） | 单容器 SQLite 降级版可零外部依赖启动 |

**关键版本**（`requirements.txt»）：fastapi 0.115.12 / uvicorn 0.41.0 / pydantic 2.12.5 /
pymysql 1.1.1 / redis 5.3.1 / jieba 0.42.1 / numpy 2.2.6 / bcrypt 5.0.0 / PyJWT 2.11.0。
向量与精排（pymilvus / torch / FlagEmbedding）是**可选档**，缺了就自动降级 —— 这是设计，不是妥协。

## 三、功能清单

### 3.1 按角色

| 角色 | 能做什么 | 数据边界 |
|---|---|---|
| 买家 `buyer» | 选店铺咨询、发起投诉、补充证据、申诉 | 只看自己发起的会话与纠纷；**看不到坐席台**（能看会话列表 = 能看别家店铺的对话） |
| 商家 `merchant» | 回买家、提交答辩、看本店处罚与信用、发起申诉、问平台规则 | 按 `shop_id» 收口 |
| 平台运营 `ops» | 案件工作台：受理投诉 → 看订单事实 → 看双方陈述 → AI 定责 → 裁决 → 处罚/复审；治理口径咨询 | 全平台 |
| 系统管理员 `admin» | 账号、模型配置、审计查看 | **不是平台方**：能改模型配置，但不能替仲裁下裁决 |

### 3.2 主链路

```
登录 → 提问 → 条款号 + 原文 + 风险等级 + 转人工
        ↓（L3 或低置信）
     人工工单 → 坐席认领 → 答复 → 或一键转平台介入
                                    ↓
                          纠纷单 → AI 定责（0.80 自动裁决线）
                                    ↓
                    自动裁决 / 转人工 → 扣分（2/12/24/48 节点处罚）
                                    ↓
                              申诉 → 维持 / 减免 / 撤销（分数回滚）
```

### 3.3 接口与页面

- **73 个 API**，按域分组：`chat» 9（会话/提问/反馈）、`auth» 5、`admin» 6、`settings» 4、
  `rules» 4、`cs» 26（客服 + FAQ + 工单）、`gov» 22（纠纷 + 处罚 + 申诉 + 店铺）；
  另有运维 `/api/health»、演示 `/api/demo/stats»、`/api/demo/ask»。
- **11 个页面**：`/login» 登录 · `/app» 工作台 · `/rules» 规则库 · `/cs» 咨询窗口 ·
  `/service» 客服坐席台 · `/dispute» 纠纷中心 · `/platform» 平台监管 · `/settings» 设置 ·
  `/admin» 系统管理 · `/legacy» 早期单页 Demo（保留对照）· `/demo» 独立演示页。
- **页面入口服务端拦截**：不是"前端藏按钮"，非授权角色访问 302 回自己首页。

### 3.4 三个咨询板块（同一页面，按角色进不同知识域）

| 板块 | 谁问 | 知识域 | 数据 |
|---|---|---|---|
| `shop» | 买家 → 店铺客服 | 店铺通用 74 / 本店专属 5 | `t_faq.audience='buyer'» |
| `rule» | 商家 → 平台规则助手 | 平台规则 21 | `audience='merchant'» |
| `gov» | 运营 → 治理规范助手 | 治理规范 20 | `audience='ops'» |

三套知识分库建索引、分域缓存 —— 不分域的话，买家和商家问"扣几分"会命中同一条答案，这是项目早期真实犯过的错。

## 四、数据库

**23 张表**（SQLite 3.2 MB / MySQL 同结构），一共约 **15,900 行**业务数据。
DDL 在 `api/schema.py»（系统表）与 `pipeline/build_sqlite.py»（规则与订单表），
两边都是 `CREATE TABLE IF NOT EXISTS» 可重复执行，不引 Alembic —— 这个规模用不上，
多一个依赖就多一个装不上的风险。

### 4.1 规则域（4 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|
| `t_rule_doc» | 8 | 11 | 规则文档：doc_name / doc_type / platform / effective_from / source_url / **file_hash**（变更扫描基线） |
| `t_clause» | 406 | 14 | 条款正文：clause_no / clause_num / clause_path / chapter / section / content / scene / risk_level / **content_hash** |
| `t_clause_version» | 409 | 6 | 条款版本：clause_id / status(active\|expired) / effective_from / effective_to / **version** |
| `t_clause_history» | 3 | 13 | 被替换的旧版正文（**不删**）：content / content_hash / version / superseded_at / batch_id |

分布：风险 **L1 266 / L2 54 / L3 86**；文档 6 部法规 + 2 份平台规则；
场景 9 类（`marketing.ad» 96、`general» 96、`governance.penalty» 74、`aftersale.return» 56 等）。

> **一个必须知道的设计约束**：`t_clause» 上有 `UNIQUE INDEX (doc_id, clause_no)»，
> 同一 (文档, 条款号) 物理上只允许一行。所以"版本历史"不能靠在主表留两行实现 ——
> 旧版正文进 `t_clause_history»，主表永远只放现行内容。这也意味着
> `t_clause_version» 是"当前版本的元信息 + 历史状态"，不是内容快照表。

### 4.2 订单事实域（2 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|
| `t_order» | 5005 | 19 | 订单：order_no / status / paid_at / shipped_at / received_at / aftersale_type / **carrier + tracking_no + picked_at** |
| `t_order_item» | 9706 | 11 | 商品明细行：order_no + line_no 唯一 / title / sku / qty / unit_price / refund_qty / refund_amount |

为什么订单表要有物流三件套：规则 2.4「上传无效运单号扣 4 分」的判定只能靠
"发货时间 vs 揽收时间"，没有 `tracking_no» 和 `picked_at» 这条规则在系统里根本无法落地。
为什么明细要单独成表：真实售后争议一半是多商品订单，"退哪几件、金额怎么摊、运费谁承担"
不是一个字段能表达的；主表的 `item_title» 那几列保留给老数据和快速列表用，
有子表行就用子表，没有就回退主表单行 —— 升级不改存量数据。

### 4.3 用户与会话域（7 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|
| `t_user» | 5 | 11 | 账号：username / email / password_hash / role(buyer\|merchant\|ops\|admin) / shop_id / status |
| `t_user_pref» | 5 | 5 | 偏好：theme / default_scene / answer_style |
| `t_shop» | 3 | 6 | 店铺：name / platform / category / contact_phone |
| `t_chat_session» | 0 | 7 | 问答会话 |
| `t_chat_message» | 0 | 10 | 问答消息（含 citations JSON、generator、latency_ms） |
| `t_feedback» | 0 | 6 | 消息级评价（message_id + user_id 唯一，一人一票） |
| `t_audit_log» | 44 | 7 | 审计：登录/失败/注册/改权限/改配置全留痕 |

### 4.4 智能客服域（5 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|
| `t_faq» | 120 | 19 | 高频问答：question / answer / category / **audience**（知识域）/ **shop_id**（NULL=平台通用）/ **cat_scope**（类目模板）/ keywords / **aliases**（同义问法，\| 分隔）/ priority / status / 审核流四列 |
| `t_cs_session» | 20 | 13 | 客服会话：shop_id / buyer_id / **scope**(shop\|rule\|gov) / status / handoff |
| `t_cs_message» | 133 | 10 | 客服消息：source（redis/faq/llm/human）/ score / faq_id / intent |
| `t_ticket» | 13 | 12 | 转人工工单：session_id / reason / question / bot_reply / status / priority / agent_id / agent_reply |
| `t_faq» 审核流 | — | — | reviewed_by / reviewed_at / review_note：人工沉淀的条目先 pending，审核后才进检索 |

> FAQ 为什么单独成表而不是塞进 `t_clause»：条款是法规原文（只读、有版本），
> 问答对是运营每天改的（可编辑、会下线），生命周期和权限完全不同。
> 又为什么有 `shop_id»：分域只解决了"谁在问"，没解决"问的是哪家店"——
> 74 条买家知识全局共享时，三家店问"什么时候发货"会拿到同一个答案，
> 店家的真实承诺反而永远答不出来。检索时合并，同问法**本店覆盖平台**。

### 4.5 平台治理域（4 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|

| `t_dispute_msg» | 26 | 7 | 纠纷沟通：role / content / kind / meta（聊天记录自动成为陈述与证据） |
| `t_penalty» | 5 | 16 | 处罚：ptype / points / **node**(2\|12\|24\|48) / basis / clause_no / auto / effective_at / expire_at / revoked_at |
| `t_appeal» | 1 | 21 | 申诉：target_type / target_id / reason / evidence / ai_view / ai_suggest / ai_confidence / result / **supplement_count + supplement_history** / review_deadline |
| `t_shop_credit» | 3 | 11 | 店铺信用：credit_score / level / points_year / dispute_count / penalty_count / **status + suspend_until** |

### 4.6 可观测与变更域（3 张）

| 表 | 行 | 列 | 说明 |
|---|---|---|---|
| `t_qa_log» | 15 | 13 | 问答审计：query / scene / risk_level / retrieved_clause_ids / cited_clauses / answer / latency_ms / cache_hit / generator / llm_ms |

### 4.7 表关系（关键外键虽未声明，但语义等价）

```
t_rule_doc 1 ── n t_clause 1 ── n t_clause_version      (clause_id)
                          └── n t_clause_history        (clause_id)
t_order    1 ── n t_order_item                          (order_no)
t_shop     1 ── n t_user                                (shop_id)
           1 ── 1 t_shop_credit                        (shop_id)
t_cs_session 1 ── n t_cs_message                        (session_id)
             1 ── n t_ticket                            (session_id)
t_dispute  1 ── n t_dispute_msg                         (dispute_id)
           1 ── n t_penalty                             (dispute_id)
t_shop     1 ── n t_dispute                             (shop_id)
t_penalty  1 ── n t_appeal                              (target_id, target_type='penalty')
```

> **未声明 FOREIGN KEY 是有意的**（SQLite 默认也不开约束），代价是孤儿数据可能被写进来。
> 目前靠接口层保证；如果要更严，可以开 `PRAGMA foreign_keys=ON» 并补约束 ——
> 但要注意两种后端的行为差异。这一条列在`docs/17»的待办里。

## 五、指标与验证（这些数是本仓库实测，不是目标值）

### 5.1 检索与问答（`eval/run_regression.py»，300 条分层评测集，SQLite + BM25 单通道 + 模板生成）

| 指标 | 值 | 口径 |
|---|---|---|
| 条款引用准确率 | **72.5%** | 答案实际引用的条款号命中 gold（层级号互认） |
| 召回率@5 | **91.8%** | gold 出现在前 5 条 |
| 时效正确率（端到端） | **85.0%** | 全部 60 道时效题里"引用对了且说出标准时限" |
| 时效一致性 | **100%** | 引用了正确条款时，答复写出该条款时限（分母 51 题） |
| 高风险漏答率 | **0%** | 60 道 L3 题全部转人工 |
| 拒答精确率 | **100%** | 说"没依据"时确实没依据 |
| 边界拒答召回 | **35%** | 20 道域外题只有 7 道正确拒答 ← **已知短板** |
| P50 / P95 延迟 | **1 / 3 ms** | 离线链路开销，不含大模型调用；**不等于并发容量** |
| token/问 | **0** | 模板路径无 LLM 调用 |

分层明细见 `reports/dashboard.html»（双击打开，纯静态）。
跨条款综合层 Top1 只有 40% 但召回@5 有 95% —— 问题在融合排序，不在召回。

### 5.2 端到端断言

`tests/cs_e2e.py» 44 / `gov_e2e.py» 64 / `board_e2e.py» 55 / `v8_e2e.py» 48 = **211 项，全通过**。
都是起真实 uvicorn、打真实 HTTP 的接口级测试，不是单元测试。

### 5.3 变更流水线

3 次真实变更留档（`docs/change_verification.md»）：版本失效（旧版 expired + 新版 v2）、
缓存失效（key `rr:v5:» → `rr:v6:»，答复内容随之变化）、门禁拦截回滚（13 条改动全部回滚，版本号还原）。
共 82 行 `t_change_log» 可审计。

### 5.4 自测发现并修掉的缺陷

6 个 P0，最严重的一个是"服务能启动、但每次提问都 500"（向量编码器缺失时链路未降级）。
清单与证据见 `docs/17-优化点扫描报告.md» 第二节。
