# 丰贸电商平台

面向电商购物的**智能客服与售后平台**：买家问得清楚、商家答得过来、平台判得公正、系统管得住。

四个端各自独立，不共用同一个工作台：

| 端 | 能做什么 | 首页 |
|---|---|---|
| **买家** | 店铺咨询 · 我的订单（含售后） · 纠纷中心 | `/cs` 店铺咨询 |
| **商家** | 规则咨询 · 经营看板 · 客服工作台 · 纠纷中心 · 知识库 | `/cs` 规则咨询 |
| **平台运营** | 治理咨询 · 客服工作台 · 纠纷中心 · 平台监管 · 知识库 | `/cs` 治理咨询 |
| **系统管理员** | 账号 / 模型配置 / 审计 · 系统指标 | `/admin` 系统管理 |

---

## 一、核心能力

### 智能客服（四级漏斗）

`Redis 精确缓存 → 知识库 BM25(≥0.88) → 大模型 → 人工兜底`

- 机器人吃掉高频问题，答不了的自动转坐席并生成工单；
- 坐席接管后机器人闭嘴，人工回复可一键沉淀成知识库条目；
- 知识按店铺隔离：`t_faq.shop_id` 为空是平台通用基线，非空是该店专属话术，同问法本店覆盖平台。

### 规则问答（RAG）

`自研 BM25(jieba) ∥ BGE-M3 向量(1024d) → RRF(k=60) → bge-reranker-large 精排 → 大模型生成`

- 每条结论必须落到一条现行有效条款上，引用编号必须出现在召回集里，否则重试一次、仍错退回模板；
- 路由分 L1 直答 / L2 附条款与免责 / L3 强制转人工（不给结论）。

### 平台监管

`买家投诉 → AI 调解定责（0.80 自动裁决线）→ 人工裁决 → 扣分累计 → 节点处罚 → 申诉回滚`

- 9 类纠纷 → 违规条款映射，扣分只查规则表，模型不参与；
- 处罚可回滚：撤销扣分连带撤销节点处罚。

### 订单与售后

- 买家在「我的订单」查订单、申请退货退款/换货、一键发起投诉（自动带好店铺与订单号）；
- 订单含商品明细（`t_order_item`）与物流三要素（承运商 / 运单号 / 揽收时间），发货后 24h 无揽收判**虚假发货**。

### 可视化

- **商家**：经营看板（本周/本月/本年销售额 + 近 14 日折线 + 客单价 + 风险/纠纷）；
- **平台运营**：纠纷按类型分布 + 待受理/待裁决/待复核申诉；
- **系统管理员**：条款风险分布（L1/L2/L3）+ 用户/会话/消息/问答 + 运行时开关。

## 二、技术栈

| 层 | 选型 |
|---|---|
| 后端 | FastAPI 0.115 + Uvicorn + Pydantic v2 |
| 数据库 | **MySQL 8**（容器端口 3307），本地无容器时自动降级 SQLite |
| 向量 | **Milvus IVF_FLAT/IP**，不可用时降级本地 npz |
| 缓存 | **Redis**（规则问答 + 客服问答 + 登录限流），不可用时降级进程内存 |
| 检索 | 自研 BM25 + BGE-M3 dense + RRF 融合 + bge-reranker-large 精排 |
| 生成 | OpenAI 兼容协议大模型（后台可配），未配置时退回模板 |
| 前端 | 原生 HTML/CSS/JS，无构建、无框架、无第三方 CDN |

## 三、快速开始

```bash
# 1. 起依赖（MySQL / Milvus / Redis）
docker compose up -d mysql8 milvus-standalone redis

# 2. 一键启动
start.bat
```

启动窗口会显示实际使用的后端，例如：

```
· MySQL 就绪

正在加载规则库与模型（首次约 15 秒，请稍候）
[√] 服务已就绪 → http://127.0.0.1:8000
```

> 依赖没起也能跑：自动降级 SQLite + 本地向量 + 内存缓存，功能不变。

## 五、数据与评测

| 项 | 规模 |
|---|---|
| 规则条款 | **406 条**（6 部法规 + 2 份平台规则），8 份文档 |
| 订单 | **5,005 单**（8 店铺 × 6 状态 × 7 售后类型），含商品明细与物流 |
| 客服知识 | 120 条（店铺通用 74 / 店铺专属 5 / 平台规则 21 / 治理规范 20） |

**当前实测指标**（300 条评测集，SQLite + BM25 单通道 + 模板生成）：

引用准确率 **72.5%** ｜ 召回@5 **91.8%** ｜ 时效一致性 **100%** ｜ 高风险漏答率 **0%** ｜ 拒答精确率 **100%**

> 开了向量 + 精排会更高，但 CI 只跑 BM25 单通道以保证可复现，所以以这组数字为准。

## 六、已知不足

**检索与生成**
- 向量 / 精排 / LLM 三层未纳入 CI 回归（CI 只跑 BM25 单通道）
- 精排在 CPU 上约 3 秒/次，生产应上 GPU 或换小号 reranker
- 无流式输出；客服侧仍是单轮打分，指代词（"这个""那个"）会丢
- LLM 通路的答案质量依赖所选模型，尚未做大模型输出的人工评分集

**平台监管**
- 纠纷类型判定是规则 + 关键词，没做小样本分类
- 检测报告只校验"有没有上传"，没有 OCR 核验
- 运单号是订单静态字段，没接物流商接口：看不到实时轨迹
- 停业到期（`suspend_until`）需要定时任务扫，当前无调度

**系统层面**
- **未上 HTTPS**，上线必须设 `COOKIE_SECURE=1` 并配证书
- CSRF 目前靠 `SameSite=Lax` 兜底，未加 token
- 登录失败计数与缓存在 Redis 不可用时落进程内存，多实例部署需强制 Redis
- 表结构靠 `CREATE TABLE IF NOT EXISTS`，改字段要手工 ALTER，未上迁移工具
- **MySQL 与 SQLite 双数据源需要手工同步**（本次交付已同步，但流程上仍有隐患）
- 会话与审计日志无备份策略

## 八、交付打包

```bash
python tools/tools_pack.py        # 产出 dist/rules_rag-1.0.0.zip + manifest.json
```

白名单收集、排除 `logs/`、`__pycache__`、`.env`、`.jwt_secret` 与临时库；
每个文件写入 sha256 清单，并做敏感文件泄漏检查。
